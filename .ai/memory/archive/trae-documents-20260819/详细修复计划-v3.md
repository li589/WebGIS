## 设计决策

### 决策 1：`test_business_regression.py` 修复策略
该文件是**独立脚本**（`if __name__ == "__main__"` 手动运行 + pytest 收集）。问题在于 `check()` 只 append 不 assert。修复需**兼容两种运行方式**：
- **pytest 方式**：`check()` 遇到失败调用 `pytest.fail()`，使 pytest 正确报告失败
- **脚本方式**：保留 `_results` 收集 + 末尾 `sys.exit(1 if failed)` 汇总
- **实现**：`check()` 改为 `assert condition, msg`，同时保留 `_results.append` 供脚本汇总。因文件顶部已 `import pytest`（L250 局部导入），将 `import pytest` 移至顶部。

### 决策 2：`artifact_router.py` 认证策略
参考 `workflow_router.py` 的 `require_workflow_run_access` 模式（L116 `_write_ok: None = Depends(...)`）。采用**一致的分层**：
- `GET /artifacts/{artifact_id}`（下载）→ 需认证（`get_request_user`），`user_auth_enabled=false` 且 development 时 loopback 可旁路（与 config 写操作一致）
- `GET /artifacts/{artifact_id}/preview.png` → 需认证
- **不新增所有权校验**（artifact 无 owner 字段，避免过度设计）；通过全局 `user_auth_enabled` 门控即可满足初代发布边界
- 复用 `app.api.error_codes.AUTH_ERROR` + `require_workflow_run_access` 的现有认证依赖，不新建

### 决策 3：`GeeContext` 锁修复策略
真实场景：`services.py` 每次工作流执行创建 `GeeContext`，`initialize()` 获取类级锁并持有到 `finally: gee_context.close()`（整个执行周期）。类级锁**意图**是防止多账号并发 `ee.Initialize` 串用同一全局运行时状态。修复：
- 将锁改为**实例级** `self._lock = RLock()`，避免账号间互斥
- `initialize()` 只在 `ee.Initialize()` 调用期间持有锁，初始化完成后立即释放（不再持有到 close）
- `close()` 移除锁释放逻辑（锁已不持有）
- **保留**：初始化失败时确保锁释放（当前 L51-53 已处理）
- 验证：`test_workflow_service.py` L1801-1802 的并发测试（FakeEeModule 双上下文）

### 决策 4：`circuit_breaker.py` 处理
探索确认 client.py 仅 L27-29、65-67 引用 circuit_breaker**常量/注释**，并未复用 registry 类。为**避免行为回归**（client.py 内联实现有类级共享锁、参数与 registry 不同），不在本轮统一两套实现（属大重构）。本轮仅：
- 确认 registry 实现是否被任何模块导入（已确认无）
- **保留**两套实现，但在 `circuit_breaker.py` 顶部添加注释说明"当前由 weatherengine/client.py 内联实现，此模块暂未接线，供未来统一使用"
- 降级为 P3，不阻塞本轮

### 决策 5：前端 `workflow-runner.ts` 类型断言
12 处 `as Record<string, unknown>` 访问 `run.layer_id` / `run.command_label`。根因：`WorkflowRunStatusResponse` 类型缺这些字段。修复：
- 在 `runtime-api.ts` 的 `WorkflowRunStatusResponse` 类型中补充 `layer_id?: string`、`command_label?: string` 字段
- 移除 `as Record<string, unknown>` 断言，改用 `String(run.layer_id ?? '')` 等安全访问
- 需同步 `openapi.json`（若该类型由 OpenAPI 生成）或直接改 TS 类型
- **注意**：运行 `npm run check:openapi` 验证契约一致

### 决策 6：前端 `console` 接入 `useLogStore`
采用 `workflow-runner.ts` 已有的 `safeLog()` 模式（try/catch 包裹 `useLogStore().logOperation`，无 Pinia 时 no-op）。**分两类**：
- **已同时调用 useLogStore 的**（settings.ts、workflow-definitions.ts、weather-tile-manager.ts 等）：删除冗余 `console.error`
- **仅 console 的**（active-layers.ts、run-layers.ts 等）：追加 `safeLog()`，保留 console 作开发调试
- 优先处理 stores 层（业务影响大），WebGL 渲染层（wind-particle、overlay-image-module）保持 console 不变

### 决策 7：fire-and-forget `.catch()`
- `workflow-timers.ts:138`：`registerExternalWorkflowRun` 移入 try 块或附加 `.catch()`
- `useWeatherCoverage.ts:54`：`refreshOverview().catch(() => {})`
- `analysis-runner.ts`：`void watchRun(...)` 内部已有终止逻辑，`drainQueue` 稳定，仅对 `watchRun` 加 `onScopeDispose` 取消令牌

### 决策 8：`ui.ts layerTimeMemory` deep watch
`rememberLayerTime()` 用展开替换引用（`layerTimeMemory.value = {...}`），引用已变。移除 `{ deep: true }` 改浅监听。**验证**：检查是否有其他原地突变路径（`delete layerTimeMemory.value[x]` 等），若有则需保留 deep。

### 决策 9：`weather-tile-manager.ts` 正则性能
`buildMergeStats` 仅用于 debug 日志。将 `cachedTiles` 计算与 `buildMergeStats` 包裹在 `if (isPerfEnabled())` 或 `if (debugLog)` 调用前判断，避免非 debug 模式下的正则开销。

### 决策 10：`useTimelineSync.ts`
- **void 强制依赖**：移除冗余 void（`currentHour`、`currentDate` 已在 body 访问），必要的保留并加注释
- **类型断言**（L341、L353）：为 `workflowProgressTimeSeek` 定义类型 `WorkflowProgressTimeSeek | null`，加 guard function
