## 四、RALPLAN-DR

### Principles
1. **证据优先**：每个「假设置」结论必须有写入→消费链的代码证据（文件:行），不做印象判断。
2. **最小外科手术**：修复只接通/对齐既有机制（hydrate 已支持的能力），不新造配置通道；gaode/bing 不接入消费（非本意）。
3. **写入≠生效必须可区分**：矩阵按 accepted（API 200）/ persisted（落盘）/ applied（服务行为变化）三态记录；重启生效项必须核对 UI 有 pending_restart/restart_level 提示。
4. **先清障后冒烟**：restart 相关实机验证前必须先解决 launcher 世代堆积（P0），否则冒烟本身制造僵尸。
5. **破坏性操作双确认**：stash drop、目录删除、进程清扫、deployment apply 均先展示预览再经用户确认。

### Decision drivers
- 验证可信度（用户核心诉求「真实可修改」）＞ 覆盖速度。
- 现有测试基建成熟（pytest 1360+ / vitest 950+），补测试边际成本低。
- 实机重启受 launcher P0 阻塞 → 冒烟必须定向、受控、可回滚。

### Viable options
**Option A：分层验证 + 分级修复 + 定向冒烟（选定）**
- 静态矩阵全覆盖 → 高价值缺口最小修复（P-A/P-B/P-C）→ 预留项标注（P-D）→ 仅对重启链/热载链做定向实机验证。
- Pros：每项结论有测试或实机证据；工作量与风险受控；顺手闭合 P0 launcher。
- Cons：gaode/bing 仍无消费（但已显式标注，符合「预留」本意）。

**Option B：全量实机逐项验证 + 全部修复（含 gaode/bing 接入瓦片代理）**
- Rejected：耗时长；受 launcher P0 与服务栈重启成本阻塞；给 gaode/bing 接消费属新功能开发，超出「验证真实性」本意，且无瓦片 URL 模板的 key 占位（tile_proxy_service.py:99-116/178-196）需新设计。

**Option C：纯静态审计报告，不修复**
- Rejected：用户已选分级修复；P-B「修改即 400」这类实锤不修则设置页持续误导。

### ADR
- **Decision**：Option A。以「验证矩阵」为主交付物，P-A/P-B/P-C 最小修复接通既有机制，P-D/P-E/P-F 以标注/记录处置，实机冒烟限定 5 项重启敏感链路。
- **Why chosen**：满足「确保真实可修改」的证据要求；修复面小且全部有 hydrate/白名单等既有机制可挂接；规避全量实机的运维风险。
- **Consequences**：gaode/bing 保持预留；Celery worker 的 log_level 仍随 worker 重启生效（本次只接 FastAPI 进程，文档注明）；前端 GeneralSettings 组件测试盲区不在本轮扩大范围（P-B 修复后现有输入框自然工作）。
- **Follow-ups**（不属本轮）：TimelineScrubber 拆分、hex 收尾、P2 backlog 剩余、真实数据 e2e、gaode/bing 若未来接入瓦片代理的设计。

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| pre-commit stash 吞未暂存改动（08-16 两次事故） | 严格执行硬约定：每轮 commit 前工作区只含本轮改动 + `git add -A` 全量；禁止 pathspec 提交 |

| worker init 钩子在 DB 未就绪时拖垮 worker 启动 | try/except 降级 + warning 日志；测试覆盖异常路径 |
