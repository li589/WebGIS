## 修复任务

### P1 — 高优先级

#### P1-1: `weather-sync-status.ts` 轮询定时器泄漏

- **文件**: `Code/frontend/src/stores/weather-sync-status.ts`
- **问题**: 第 70 行 `setInterval(pollTaskOnce, 3000)` 创建的定时器在用户关闭设置面板后不会被自动清理。Store 作为 Pinia 单例无 `onScopeDispose` 绑定，`stopPolling()` 依赖调用方手动触发。
- **修复**: 在使用 `startPolling` 的组件（`DataSourceSettings.vue` 或 `WeatherProviderSettings.vue`）的 `onBeforeUnmount` 中确保调用 `stopPolling()`；同时在 Store 中添加 `$dispose` 钩子作为兜底。
- **验证**: `cd Code/frontend && npm run test -- weather-sync`

#### P1-2: `workflow_router.py` 空操作异常处理器

- **文件**: `Code/backend/app/api/routers/workflow_router.py` 第 145-146 行
- **问题**: `except Exception: raise` 是 catch-and-rethrow 空操作，不记录日志、不清理资源、不转换异常类型，仅在 traceback 中增加无关帧。
- **修复**: 删除 `except Exception: raise` 块，保留前面的 `except ValueError` 分支。
- **验证**: `Env/Python312/python.exe -m pytest Test/backend/test_workflow_routes.py -q`

#### P1-3: `import_router.py` 宽泛异常处理可能泄露内部路径

- **文件**: `Code/backend/app/api/routers/import_router.py` 第 193、218、316、337、374 行
- **问题**: 5 处 `except Exception as exc` 将 `str(exc)` 直接写入 HTTP `detail`，rasterio/pyproj 异常可能包含绝对路径和内部错误信息。
- **修复**: 将 `except Exception` 收窄为具体异常类型（`rasterio.errors.RasterioIOError`、`rasterio.errors.RasterioError`、`pyproj.ProjError`）；对无法收窄的，在日志中记录完整异常，在响应中返回脱敏消息。
- **验证**: `Env/Python312/python.exe -m pytest Test/backend/test_import_raster_crs.py Test/backend/test_import_data_io.py -q`

#### P1-4: `workflow-runner.ts` 429 重试定时器缺少全局清理

- **文件**: `Code/frontend/src/stores/layers/workflow-runner.ts` 第 1089-1095 行
- **问题**: `window.setTimeout` 创建的 429 重试定时器存入 `deps.workflowRetryTimers` Map，但缺少页面卸载/路由切换时的全局清理。`interruptWorkflowForCatalog` 仅按单个 catalogId 清理。
- **修复**: 在 Dashboard 组件的 `onBeforeUnmount` 中遍历 `deps.workflowRetryTimers` 并 `clearTimeout` 所有待处理定时器；或在 Store `$dispose` 中统一清理。
- **验证**: `cd Code/frontend && npm run test -- workflow-runner`

## 假设与决策

1. **P1-3 修复策略**: 优先收窄异常类型而非脱敏处理，因为收窄后能更精准地返回正确 HTTP 状态码。对无法收窄的异常，在服务端日志中保留完整 traceback，在响应中返回通用错误消息。
2. **P2-1 修复范围**: 仅替换可直接映射到已有契约类型的 `any`；对于需要新建接口的复杂场景，标记为后续迭代。
3. **P2-2 修复范围**: 不全量修改 50+ 处 `except Exception`，仅审查 `config_*` 和 `gee_bridge_service.py` 中可能吞没关键错误的实例。已有 `# noqa: BLE001` 标注的保留。
4. **P2-3 修复策略**: 评估而非直接修改 — deep watch 的替代方案需要基于实际性能分析数据决定，不盲目重构。
5. **前端验证**: 使用 Browser 插件优先验证渲染行为（如可用），否则使用 Playwright 兜底。
