  2. Celery worker **不热载**，改 worker 代码必须重启 worker 进程。
  3. ⬛ Open-Meteo named volume **禁** bind mount（A5，Windows errno 95）；数据盘 bind mount 是允许的，勿混。
- 附带**四类改动生效代价矩阵**（源码 / 前端 / 配置 / 依赖 / 镜像内系统工具）与 `compose.override.dev.yml` 草案。

### 新发现：两个**面向交接机**的平台缺陷（都真实、都可复现）

**1. LF/CRLF：`core.autocrlf=true` 会把交付资产 checkout 成 CRLF。**
- 现象：`.gitattributes` 原先只覆盖 `Code/frontend/**` 与 `Test/frontend/**`，**没覆盖**
  Dockerfile / compose / `*.conf` / `*.sh`。
- 危害（非纯外观）：
  - Dockerfile 里 `\` 续行若尾随 `\r`，下一条指令被污染；
  - shell 脚本在 Linux 下 `bash x.sh` / `./start.sh` 直接 `\r: command not found`。
    而 AGENTS.md 明确写着 Linux 用 `./start.sh`。
- **关键结论（省了大量无效改动）**：`git ls-files --eol` 显示这些文件的**索引 blob 本来就是 LF**
  （`i/lf`），CRLF 只存在于本机**工作树**（`w/crlf`）。⇒ 加 `eol=lf` 规则**不产生任何内容 diff**，
  只改变未来 checkout 的落地形态。**零 churn 修掉一整类跨平台故障**。
- 处理：`.gitattributes` 增加 `**/Dockerfile`、`**/Dockerfile.*`、`**/.dockerignore`、
  `**/compose*.yml`、`**/docker-compose*.yml`、`Code/**/*.conf`、`**/*.sh` → `text eol=lf`。
- 实测佐证：把两个 Dockerfile 强制转成 CRLF 后跑 `docker build --check` **仍然通过**
  （BuildKit 会归一化行尾）⇒ Dockerfile 虽有余量，但 shell 脚本没有，故仍要钉 LF。

**2. 可执行位缺失：`start.sh` / `stop.sh` / data-sync 下 4 个 `.sh` 的 mode 是 `100644`。**
- 危害：Linux 下文档写的 `./start.sh` 直接 **Permission denied**（Windows 文件系统不记录 +x）。
- 处理：`git update-index --chmod=+x` → `100755`，6 个脚本已入库。
- 注：`git reset` 会连同 `--chmod` 改动一起回退（mode 只活在索引里），所以**不要在
  `--chmod` 之后 `git reset`**。

### 校验（提交前一次性跑齐）
`ruff check launch/` → All checks passed；`py_compile` 4 个改动模块 → OK；
`docker build --check` 两个 Dockerfile → no warnings；`docker compose -p cgda -f docker-compose.yml
-f compose.prod.yml config --services` → EXIT=0，14 服务；`nginx -t` → successful。
`ruff format --check` 报 6 个文件 would reformat，但对照 `git show HEAD` 基线确认是**改动前就存在**
的既有偏差，故意不跑 format（会动无关行）。

### 教训（本轮新增）
- **提交前先看 `git ls-files --eol`**，别凭 `grep $'\r'` 就断定要重写内容：工作树 CRLF ≠ 索引 CRLF，
  前者加 `.gitattributes` 即可，后者才需要 renormalize。差一步就会制造整仓行尾 churn。
- **Mode 改动只存在于索引**，任何 `git reset` 都会静默回退，务必在同一个提交流程内完成。

  图标文件也在。⇒ **无需合并**。

### 根因：`origin/main` 的本地引用是"假相"，来自过窄的 fetch refspec
- 原配置：`remote.origin.fetch = +refs/heads/dev:refs/remotes/origin/dev` —— **只跟踪 dev**。
  ⇒ `git fetch origin main` 只更新 `FETCH_HEAD`，**不更新** `refs/remotes/origin/main`；
  该 ref 长期停在 `352d2be8`(2026-09-08)，而真实远端 main 已是 `85431991`(2026-09-16)。
- 这会让人在 IDE 的 Git 面板 / `git branch -v` 里看到"远端另一个状态"，**误判为远端被改**。
- 处置：改为标准 `+refs/heads/*:refs/remotes/origin/*`，`git fetch origin --prune` 后
  `origin/main` 正确落到 `85431991`。
- **教训**：判断远端状态**一律用 `git ls-remote`**（实时）或确认 refspec 覆盖目标分支；
  不要相信 `origin/<branch>` 这个本地缓存 ref。
