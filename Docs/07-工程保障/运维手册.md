### 1.2 硬前置（Windows）

- Docker Desktop 与启动终端**必须以管理员身份**运行（否则镜像/volume/端口访问可能异常）。

## 2. 标准操作流程（SOP）

### 2.1 全量启动

```bat
.\start.bat
:: 等价：Env\Python312\python.exe launch.py start
```

启动顺序：清理编译缓存 → 刷新 `catalog-seeds.generated.json` → Docker 栈（redis/minio/minio-init/open-meteo）→ Redis/MinIO 就绪探测 → 9 Workers → Beat → FastAPI（HTTP 就绪探测，最多 30s）→ Nginx Gateway。

- 改前端后需重建 dist：`launch.py restart --rebuild-frontend`（或手动 `npm run build`）。
- 前端 HMR 开发：`launch.py start --vite`（入口仍 `:5175`，Gateway 同域代理 Vite `:5174`）。

### 2.2 分组件操作

| 命令 | 作用 | 使用时机 |
|------|------|----------|
| `launch.py start fastapi` | 仅 FastAPI | 改后端代码后快速联调 |
| `launch.py restart backend` | 重启 FastAPI + 全部 Worker + Beat（不动 Docker/Gateway/Vite） | 改 `BACKEND_DATA_ROOT` 后必用 |
| `launch.py reload gateway` | Nginx 配置热重载（`nginx -t` + reload，不重建容器） | 改 gateway nginx.conf / CSP |
| `launch.py start gateway [--rebuild-frontend]` | 仅 Gateway | 前端静态资源重建 |
| `launch.py stop [component]` / `status` / `logs [component] [-n N]` | 停止 / 状态 / 日志 | 日常巡检 |
| `launch.py clean-cache` | 清 `__pycache__`/`.pyc` + Vite `.vite`（**不碰 Redis**） | 缓存异常时 |
| `launch.py flush` | **高风险**：Redis `FLUSHDB` + 删天气文件缓存 | 仅排障；**永不**由 start/restart 自动执行 |

> start/restart 默认按组件矩阵自动 clean-cache（`--no-clean-cache` 跳过）。缓存分层细节见 [联调缓存与生效边界](联调缓存与生效边界.md)。

## 4. 日志体系

| 日志 | 内容与读法 |
|------|-----------|
| `fastapi.log` | uvicorn 输出。注意区分 `Started reloader process [pid]`（热重载父进程）与 `Started server process [pid]`（实际 worker）；`WatchFiles detected changes ... Reloading...` 后**必须有新的** `Application startup complete`，否则重载挂死（见 §9.1） |
| `worker-<name>.log` | 各队列 Celery Worker；任务卡住先看对应队列 worker |
| `beat.log` | 定时调度器 |
| `launcher_pids.json` | 启动器保存的进程 PID 表（stop 按 PID 优雅终止） |

日志轮转：`launch.py` 启动时自动 rotate（`rotate_subprocess_log_if_needed`）；手动看尾部 `launch.py logs fastapi -n 200`。

## 5. 按症状排障

> 处理原则：先看 [§6 端口与网络专章]（本机两大历史故障都在这里），再按下面症状树定位。

### 5.1 启动类

| 症状 | 首查 | 详见 |
|------|------|------|
| `docker compose 启动失败: ... bind: An attempt was made to access a socket in a way forbidden by its access permissions` | 端口被 WinNAT 排除段吞掉（非占用！） | §6.2 / §9.2 |
| `bind: address already in use`（或 10048） | 端口被真实进程占用：`netstat -ano \| findstr :<port>` 找 PID | §6.1 |
| FastAPI `未在 30s 内就绪`，且日志停在 `Reloading...` 无后续 | 重载挂死：环回 TCP 被安全软件丢弃，或 worker 崩溃无输出 | §9.1 / §6.3 |
| `deployment.config ... fail-closed` 拒启 | 部署配置损坏：按错误信息用 `.bak.1/.2/.3` 轮换恢复 | AGENTS.md 高风险区 1b |
| `BACKEND_DATA_ROOT/OUTPUT_ROOT is required outside development` | 数据根未配置（production/test fail-fast） | 检查 `Code/backend/.env` |
| Worker 启动后不消费任务 | Redis 连通性（16379）；`worker-*.log` 里 bootstrap 错误 | §3 / §4 |

### 5.2 运行类

| 症状 | 首查 |
|------|------|
| 前端白屏 / 静态资源 404 | Gateway dist 是否重建（`--rebuild-frontend`）；Cesium 静态走 `/cesium/` 精确匹配（禁止 SPA 回退） |
| `:5175` 报 CSP 拦截而 Vite 直连正常 | `Code/infra/gateway/nginx.conf` 引用的 `security-headers.conf`（`unsafe-eval` + `wasm-unsafe-eval` 给 Cesium），改后 `reload gateway` |
| 天气瓦片 502 / 空瓦片 | `cgda-open-meteo` 容器状态；本地源数据需 `launch.py sync`；`visibility` 非 `gfs_global` 常为 data-empty（模型缺口，非故障） |
| 改了配置不生效 | 对照 [联调缓存与生效边界](联调缓存与生效边界.md)：FastAPI 进程即时 vs Worker 需新世代（`restart backend`） |
| 登录/会话异常 | Redis（会话集中存储）；角色/密码/主题变更会吊销该用户全部会话与 Token（预期行为） |
| 导入任务 404/507 | staging 生命周期（TTL 24h/完成滞留 30min）与配额回收；`I:\...\ProjectOutput\imports\_staging` |

### 5.3 测试类

| 症状 | 处置 |
|------|------|
| pytest 文件删除类测试假阳性失败（`test_import_data_io`/`test_resumable_upload` 等） | WorkBuddy safe-delete shim 拦截删除并 fail-closed——用前缀禁用：`CODEBUDDY_SESSION_ID= CLAUDE_SESSION_ID= CODEBUDDY_SAFE_DELETE_SANDBOX= Env/Python312/python.exe -m pytest ... -p no:cacheprovider --basetemp="Test/.pytest-be"` |
| `test_archive_safe.py` 报 UnRAR 缺失 | 需要 `Code/backend/vendor/unrar/win-x64/UnRAR.exe`（gitignore；rarlab 下载 `unrarw64.exe -s -d` 解出 CLI）；CI 用 `apt install unrar` |
| 前端测试 `Test/frontend` 找不到 | vitest 从 `Code/frontend` 启动（vite.config `test.include` 跨 root 加载），命令 `cd Code/frontend && npm run test` |

## 6. 端口与网络专章

### 6.1 端口清单与占用判定

| 端口 | 归属 | 改动面 |
|------|------|--------|
| 8000 | FastAPI | `Code/backend/.env`（HOST/PORT）+ Gateway 反代目标 |
| 5175 / 5174 | Gateway / Vite | `Code/infra/gateway/docker-compose.yml`、`vite.config.ts` |
| 8080 | Open-Meteo 宿主映射 | compose 已参数化 `OPEN_METEO_HOST_PORT`；**但**后端本地源 URL 硬编码 `http://127.0.0.1:8080`（`provider_ids.py:17`），改端口需两处同步 |
| 9100 / 9101 | MinIO API / Console | runtime compose |
| 16379 | Redis 宿主（容器内 6379） | runtime compose；**刻意避开 Hyper-V 动态保留段** |

**占用 vs 被系统保留**（关键区分）：

| 报错 | 含义 | 判定 |
|------|------|------|
| `address already in use` / 10048 | 真实进程占用 | `netstat -ano | findstr :<port>` 能看到 LISTENING + PID |
| `An attempt was made to access a socket in a way forbidden by its access permissions` | 端口在 WinNAT/Hyper-V **排除段**内，任何进程都绑不了 | netstat 上无监听，但 bind 失败 → §6.2 |

### 6.2 WinNAT 动态排除端口段（高频坑）

机制：Hyper-V/WSL2/Docker 运行期间，WinNAT 会动态保留一批 **100 端口宽**的 TCP 段（本机实测从 6309 起就有分布），且每次重启/网络栈变化会**重新洗牌**。落在段内的业务端口全部无法绑定，报错即 §6.1 的 "forbidden by its access permissions"。

**检查**：

```powershell
netsh interface ipv4 show excludedportrange protocol=tcp
# 输出 [开始端口 结束端口] 区间列表；逐一比对业务端口是否落入
```

**处置（管理员）**——立即恢复三连：

```powershell
net stop winnat                # 释放全部动态排除段
docker start cgda-open-meteo   # 或重跑 .\start.bat（此时绑定能成功）
net start winnat
```

**持久预防（推荐一次性执行）**——把动态端口范围归位到 Windows 标准高位段，低位业务端口（8000/5175/8080/9100/16379）从此不会被动态段吞掉：

```powershell
netsh int ipv4 set dynamicport tcp start=49152 num=16384
# 之后重启一次机器生效
```

> 本机基线（2026-09-06）：动态段从 6309 起分布，8080 曾落入 `8042–8141`——动态范围明显被压低，建议尽快归位。若个别排除段带 `*`（管理保留），`net stop winnat` 不释放，需 `netsh int ipv4 delete excludedportrange protocol=tcp startport=<s> numberofports=<n>` 显式删除。

**改端口的联动清单**（如确需调整 Open-Meteo 宿主端口）：compose `OPEN_METEO_HOST_PORT` + `provider_ids.py` 的 `OPEN_METEO_LOCAL_URL` + `AGENTS.md`/文档中的 8080 引用 + `launch.py sync` 依赖的本地源可达性。

### 6.3 环回（loopback）入站被安全软件丢弃

症状：进程对 `127.0.0.1`（含自身绑定的端口）**connect 超时**（非拒绝）；典型后果——uvicorn/asyncio 在 Windows 上创建 Proactor 事件循环需要 socketpair 环回握手，环回被丢 → 事件循环创建永久阻塞 → FastAPI 零输出不监听（详见 §9.1）。

**判定（管理员不必需）**：

```powershell
# 三个不同运行时自连测试——全部超时 = 环回入站被系统性丢弃
python  -c "<§10 自连脚本>"
node    -e "<§10 node 版>"
powershell -c "<§10 PS 版>"
# 同时核对 Windows 防火墙：netsh advfirewall show allprofiles state
# 并检查常见安全软件进程：360rps / 360sd / 360rp / huorong / hips ...
```

**处置**：退出/暂停安全软件的"网络防火墙 / 局网防护"模块（360 用户：设置→安全防护中心→关闭网络防火墙，或直接退出 360 全家桶）后复测自连脚本，CONNECT OK 即恢复。

> 注意区分：Windows 防火墙对**环回流量默认不过滤**（专用配置文件关闭时可排除）；此症状基本都来自第三方安全软件的 WFP 过滤层。

## 7. 数据面运维

- **数据根**：`BACKEND_DATA_ROOT` / `BACKEND_OUTPUT_ROOT` 是数据面真源；production 空根拒启；**禁止**代码静默回退盘符。修改入口：部署配置中心 `/deployment`（仅 admin，`PUT /config/deployment` preview→apply→`POST /config/service/restart`），改后 `launch.py restart backend`。
- **Open-Meteo volume**：`backend_open-meteo-data` 落在 Docker Desktop VHDX 内（本机 `I:\Docker\DockerDesktop`），**勿用 Windows 路径 bind mount 替代**（Windows errno 95）。运行栈（`-p backend`）与同步栈（`-p data-sync`）共享同一 volume 但 compose project 不同，勿混用 project 名。
- **同步**：`launch.py sync [job]`（默认 `open-meteo-sync`，一次性容器写共享 volume）；`visibility` 需 `gfs_global` 域。
- **导入 staging 生命周期**（自动，无需人工）：未完成 TTL 24h；已完成滞留 30min；配额紧张时压力清理；配额默认 100 GiB（`BACKEND_MAX_IMPORTS_TOTAL_BYTES`），回收策略**绝不删除**用户 `imported-*`。
- **反馈闭环**：用户反馈落盘 `BACKEND_DATA_ROOT/_runtime/feedback/CGDA-BUG-*/`；处理流程见 `.ai/rules/feedback-triage.md`（`Env\Python312\python.exe Tools/feedback_triage.py --open`）。

## 9. 事故记录（Incident Log）

> 模板：**现象 / 根因 / 证据链 / 处理 / 验证 / 预防**。按时间倒序追加。

### 9.2 2026-09-06：`cgda-open-meteo` 启动失败——端口 8080 被 WinNAT 动态排除段吞掉

- **现象**：`start.bat` 中 redis/minio 正常 Running，open-meteo 卡 `Created`；docker compose 报
  `ports are not available: exposing port TCP 127.0.0.1:8080 ... bind: An attempt was made to access a socket in a way forbidden by its access permissions.`。用户观察为"Docker 已在运行时启动失败"。
- **根因**：Hyper-V/WinNAT 动态 TCP 排除段 `8042–8141` 恰好覆盖 8080（`netsh interface ipv4 show excludedportrange protocol=tcp` 实证）；排除段内端口任何进程都无法绑定。与"Docker 是否已运行"无因果关系——WinNAT 排除段随 Hyper-V 生命周期动态洗牌，redis/minio 端口（16379/9100/9101）不在段内故无感。`netstat` 上 8080 无监听进程（区别于真实占用的 `address already in use`）。
- **处理**（管理员，待执行确认）：`net stop winnat` → 启动容器 → `net start winnat`；持久修复 `netsh int ipv4 set dynamicport tcp start=49152 num=16384` + 重启（本机动态段从 6309 起分布，已被压低）。
- **预防**：低位业务端口统一依赖归位后的标准动态范围（49152–65535）；Open-Meteo 宿主端口有 `OPEN_METEO_HOST_PORT` 逃生门，但后端 `OPEN_METEO_LOCAL_URL` 硬编码 8080，改端口需联动（见 §6.2）。

### 9.1 2026-09-03：FastAPI 启动挂起（30s 未就绪、worker 零输出）

- **现象**：`start.bat` 其余组件正常，FastAPI 停在 `Started reloader process [pid]` 后无 `Started server process`、无任何报错；`launch.py start fastapi` 可稳定复现；端口 8000 从不 LISTEN。
- **根因**：第三方安全软件（360 全家桶，进程 360rps/360sd/360rp 实测在跑）的 WFP 过滤层**丢弃环回入站 TCP**。Windows 上 asyncio 创建 Proactor 事件循环需经 loopback socketpair 握手（`socket.py::_fallback_socketpair → accept()`），环回被丢 → 事件循环创建永久阻塞 → worker 未起即挂死（faulthandler 栈转储实证卡在 `new_event_loop`）。
- **证据链**：python / node / powershell 三个不同运行时对 `127.0.0.1` 与 `::1` 的自连**全部 connect 超时**（连未监听端口也是超时而非拒绝，说明是丢包而非无监听）；Windows 防火墙专用配置文件为关闭（排除系统防火墙）；排除段不含测试所用的临时端口（排除另一解释）。
- **处理**：退出/暂停 360 的网络防火墙（或整个 360）。
- **验证**：重跑 §10 自连脚本应 `CONNECT OK`；`start.bat` 后 `fastapi.log` 出现 `Application startup complete` 且 `curl /health` 返回 200。（**此事故的处置动作待复验**——根因判定在会话内已闭环，修复由用户侧执行。）
- **预防**：排障期安全软件白名单化 `Env/Python312`、`com.docker.backend`、nginx；症状复现时先跑自连脚本再查应用日志。
