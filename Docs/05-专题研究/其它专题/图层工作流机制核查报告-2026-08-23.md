## 1. 图编译"双机制"核查 —— 实际是"一编译器 + 三执行器"

### 1.1 事实链：compiler 的真实消费面

`compile_litegraph_to_workflow_definition`（`app/services/workflow_graph_compiler.py:130`）全部调用点：

| 调用点 | 性质 |
|---|---|
| `app/api/routers/workflow_definition_router.py:32,69,105` | 编辑器端点 `/workflow-definitions/compile` |
| `app/services/workflow_request_resolver.py:894-907`（`_compile_workflow_seed`） | **主链** |
| `app/services/python_provider_request_builder.py:135-154` | **主链（关键证据）** |

`python_provider_request_builder.py:134-154`：algorithm 通道下，`workflow_name` 若无显式 definition，则调 `_compile_workflow_seed` 把 LiteGraph seed 编译成 `workflow_definition` 注入 job_request。**compiler 是 algorithm 通道的必经组件，非旁路、非死代码**（确认）。

### 1.2 事实链：三个平行 DAG 执行器

| 执行器 | 位置 | 服务通道 | 存活状态 |
|---|---|---|---|
| ① `WorkflowExecutor` | `app/workflow_engine/executor.py:20` | weather（`WeatherWorkflowService`，`app/weatherengine/workflow_service.py:6,40`） | **生产内核**，经 `weather_bridge_service.py:26-31` 惰性加载接入 bridge 链第 2 位；开关 `BACKEND_WEATHER_WORKFLOW_ENABLED`（`app/core/config.py:543-545`，默认 true）。**全仓测试零引用** |
| ② `WorkflowExecutor`（gee） | `app/gee/core/src/webgis_gee/workflow/executor.py:30` | gee（`WorkflowService`，`application/services.py:59,98` → `gee_bridge_service.py:132-204,273`） | 生产内核，bridge 链第 1 位 |
| ③ python provider 图执行 | 算法包 `Code/algorithms/providers/Python/workflow/`（graph/executor/presets） | algorithm（`python_provider_bridge_service`） | 生产内核，bridge 链第 3 位 |

`app/workflow_engine/` 的 models/registry/base/schema 被 weatherengine/nodes 体系整体使用，**非遗留目录**。

### 1.3 seed 双格式解读：静默失配史（已实锤 3 处补丁）

同一 seed JSON 存在两种解读并存：

- **编译路径**（algorithm 通道）：`get_definition` → compiler → `node_type="module"+params.module_name`，**丢失原始前缀**（`workflow_request_resolver.py:685-701` 注释明确记载 download/* 前缀丢失，被迫用注册表反查补丁）。
- **原生 LiteGraph 路径**（resolver 展平）：`module/*` 前缀直接判定（`resolver.py:726-744`）。

已发生的静默失配实例：
1. compiler 曾丢弃 seed `extra`（group_title/output_labels）→ 前端建组配置静默失效，后在 `resolver.py:911-917` 补透传（即 2026-08-23 上午 `5546355` 修复的根源）。
2. fan-in edge 丢弃规则在 `compiler.py:31,109-127` 与 `resolver.py:804-811` **两处各自维护**。
3. download/* 前缀丢失靠注册表反查补丁（`resolver.py:685`）。

### 1.4 判定

- **"双机制冗余"实际风险：中**。(A)(B) 并非同一职责的重复实现——compiler 是**格式转换器**，三个 executor 分属 gee/weather/algorithm 三个引擎通道，当前无运行时冲突。真正的风险是：
  - **seed 字段约定演进时双解读失配**（历史 3 处实锤，会继续发生）；
  - weather 通道执行内核（workflow_engine/executor.py）**零测试引用**，属脆弱点。

**建议方向**（供决策，未实施）：统一 seed 编译为单一入口（compiler 成为唯一解读方，resolver 不再自展平）；给 workflow_engine 补测试。**不建议删除任何一方**——三者都是活的生产组件。

## 2. Celery 队列配置核对

### 2.1 派发侧映射表（`app/tasks/workflow_tasks.py:121-140` + `app/core/config.py:407-455,514-557`）

| channel | realtime | standard | heavy | batch |
|---|---|---|---|---|
| gee | gee-realtime | gee-standard | gee-heavy | gee-batch |
| weather | weather-realtime | weather-standard | weather-heavy | weather-batch |
| algorithm | realtime（共用） | standard（共用） | heavy（共用） | batch（共用） |
| analysis | realtime（共用） | standard（共用） | heavy（共用） | batch（共用） |
| download | download-realtime | download-standard | —（miss） | —（miss） |

18 个 key 收敛为 **14 个实际队列名**。查表 miss（download×heavy/batch）fallback 到 `workflow_queue_analysis_standard`（`workflow_tasks.py:172-174`，有 worker），且 queue_tag 白名单（:181-204）会拒绝该组合，逻辑自洽。

### 2.2 worker 部署清单（`launch/constants.py:64-76` + `launch/process_manager.py:105-115`）

| worker | -Q | 实例数 |
|---|---|---|
| realtime | realtime | 1 |
| standard | standard | 2 |
| heavy | heavy | 2 |
| batch | batch | 1 |
| download | download-realtime,download-standard | 1 |
| gee | gee-realtime,gee-standard,gee-heavy,gee-batch | 1 |
| weather | weather-realtime,weather-standard,weather-heavy,weather-batch | 1 |

**交叉核对结果：派发侧 14 队列与 worker 监听 14 队列完全一一对应**。无"派发无人消费"，无"监听无人派发"。Beat 定时（`celery_app.py:186-250`）路由到 weather-standard/weather-batch/standard/batch 全部有 worker；无裸 `.delay()` 调用（全仓仅 2 处 apply_async 均显式指定 queue）。`process_workflow_run` 的 acks_late/reject_on_worker_lost/acks_on_failure_or_timeout（`workflow_tasks.py:214-219`）为 per-task 声明，全 worker 统一。

### 2.3 风险清单

| # | 缺口 | 严重度 | 证据 |
|---|---|---|---|
| 1 | worker 队列名**硬编码**在 `launch/constants.py:64-76`，派发侧可被 env `BACKEND_WORKFLOW_QUEUE_*` 覆盖（`config.py:407+`）→ 改 env 不改 constants = 派发无人消费 | **中** |
| 2 | Celery app 无 `task_default_queue`/kombu Queue 声明（`celery_app.py:40-111`）——现有派发点均显式指定，但**新增任务漏指定会落到默认 `celery` 队列且无 worker**；`import_jobs.py:89` 的 `"celery"` fallback 是误导性死代码 | **中** |
| 3 | acks_late 仅 workflow task 有；download follow-up（`download_tasks.py:101-105`）等未设，worker 崩溃时消息已 ack 即丢 | 中 |
| 4 | download follow-up 队列由 workflow payload 查表决定（`follow_up_dispatch_service.py:63,76`），可能落入 standard 等非 download 队列，与 download worker 分工设计不齐 | 低 |
| 5 | realtime 单实例 + Windows solo 池串行（`config.py:648`），高优任务仍可能排队 | 低 |

**建议方向**：以 settings 单一来源生成 worker 队列清单（消除硬编码漂移）；补 `task_default_queue` 兜底并清理 `"celery"` fallback。

## 3. materialize-map-layers 产物→overlay 映射规则

### 3.1 端到端流程

```
POST /workflow-runs/{id}/materialize-map-layers（workflow_router.py:340-371）
  → require_workflow_run_access + _deny_if_not_run_owner
  → python_provider_result_builder.materialize_map_layers（builder:1009+）
      → 取 result_dto.products（空则从 result_ref.inline_data 回捞，builder:1009-1017）
      → 状态白名单 {succeeded,running,accepted,queued}，否则 409（builder:997-1000）
      → 按 product 类型分流：
          A. omega_* .mat 单文件 → commit_science_raster_variable（builder:762）
          B. omega_*_block_dir 目录 → upsert_block_dir_timeseries（builder:672）
          C. raster/map_layer GeoTIFF → commit_algorithm_geotiff（builder:863）
      → register_geotiff_as_imported → IMPORTS_DIR/<layer_id>/ + register_overlay
        （raster_register.py:212-227）
  → 响应 {run_id, layers:[{overlay_layer_id,title,product_tag,bounds,source_crs,
     cog_preview_url,time_list,default_time,native_step}], count}（builder:1061-1082,1170）
```

### 3.2 映射规则表

| 项 | 规则 | 证据 |
|---|---|---|
| layer_id（block 序列） | `imported-{sha1(layer_key或run_id, canon_label, variable)[:12]}`；同工作流重跑**覆盖同层** | raster_timeseries.py:84-86,101,241-243 |
| layer_id（.mat 单文件） | `stable_import_layer_id(...)`，overwrite 复用已有目录 | raster_commit.py:105-122,171-178 |
| layer_id（generic GeoTIFF） | 硬编码 `imported-gis-{run_id[-8:]}-{index:02d}`，overwrite | builder:865-867 |
| 幂等性 | 稳定哈希 layer_id + overwrite 策略，重复调用不堆积新层 | 同上 |
| 文件引用 | .mat 抽变量→临时 GeoTIFF→复制入 IMPORTS_DIR；block 目录**原地引用**（增量 upsert+文件锁）；generic tif 复制 | raster_commit.py:158-200；raster_timeseries.py:244-248 |
| palette/vmin/vmax/unit | omega 系列来自硬编码表 `_MAPPABLE_PRODUCTS`（builder:46-74）；generic 一律 viridis；**registry 侧写死 palette="wind-blue"、vmin/vmax=None**（raster_register.py:156-158,221） |  |
| bounds | rasterio 读 `dataset.bounds` 转 EPSG:4326 | raster_register.py:85,137 |
| 多产物 | 全部上图；存在 omega block 序列时跳过 omega_pixel（防一个 run 出四层） | builder:592-611 |
| catalog 关系 | **动态 overlay，不入 catalog_seeds**；注册进 overlay_registry（目录即注册态）。前端凭响应 `overlay_layer_id + cog_preview_url(/overlay-preview/{id}) + bounds` 触发 addImportedRasterLayer，可附 `?palette=&min_value=&max_value=` | builder:735 注释 |

`python_provider_result_builder` 是**双用途**：运行时 bridge 在 submit_job 成功后调 `build_result_refs` 生成 result_refs（map_layer 请求时内联发布，builder:185-205）；materialize 端点复用同一 `build_product_map_layer_refs`（builder:1043）。ref 结构：`result_id="algorithm-map-{index}-{run_id[-8:]}"`，`result_kind=map_layer`，`inline_data={render_hint, layer_assets{overlay_layer_id, cog_url, cog_bbox, source_path, time_list}}`（builder:726-747,810-828）。

**通道差异**：materialize 仅适用 algorithm 通道。weather 运行时直接带 `render_hint`（spec 来自 `WEATHER_LAYER_SPECS`，weatherengine/constants.py:52-57，service.py:428-437），heatmap 走 geojson ref；GEE 走独立瓦片代理（unified_tile_router.py:31 TILE_URL_TEMPLATES）——均不经此端点。

### 3.3 风险清单

| # | 脆弱点 | 说明 |
|---|---|---|
| R1 | **palette 断裂** | render_hint.palette（cividis 等）与 registry 写死的 wind-blue/vmin=None 不一致 → 拉伸/图例失真 |
| R2 | **硬编码白名单静默丢弃** | 新 product type 不在 `_MAPPABLE_PRODUCTS` 且 type/tags 不匹配 raster 时返回 None 被静默丢（builder:626-641） |
| R3 | **路径/文件名耦合** | fallback 硬编码 `products/omega_sf_fenkuai` 双路径（builder:1103-1111）；`^\d{8}\.mat$`、glob `????????_????????.mat` 命名约定（builder:76,1113） |
| R4 | **title 英文模板** | `Algorithm Map Layer: {layer_tag}` / `Algorithm Output: {layer_label}`（Celery ASCII 限制，builder:356,411 ascii-ignore 剥离中文）——即近期中文 title 问题的根因 |
| R5 | **generic 层 id 含 index** | 两次产物数量/顺序变化时 index 错位，旧 imported-gis 层残留 |

## 4. 天气 seed 双路径核查

### 4.1 linked_layer_id 消费面

| 消费点 | 位置 | 用途 |
|---|---|---|
| seed 定义 | workflow_seeds/system/weather_wind_field_demo.json:10（temperature 同构） | `_meta.linked_layer_id` 指向 `wind-field` |
| 校验器 | layer_workflow_validator.py:219-234（Rule 2, error 级）+ :236-259（Rule 6 节点级） | 校验图层存在性，防链接漂移 |
| 定时器 | workflow_timer_service.py:316 | 提交 payload 的 layer_id 兜底 |
| 定义服务 | workflow_definition_service.py:159,179,291,344,393-394 | 创建/同步/透传 `_meta` |
| 前端编辑器 | WorkflowEditorPanel.vue:191,403；workflow-output-layers.ts:6；workflow-definitions.ts:108 | 编辑器回填 layerId、产出图层归组展示 |
| 规范 | Docs/03-规范协议/workflow_seed_conventions.md:36 | "定时器 / 状态 UI 可用" |

**设计用途：展示/关联元数据，非执行路由键。**

### 4.2 提交天气图层的实际走向

resolver：weather descriptor（`weather_descriptors.json`，`source_type=weather`，**无 engine、无 workflow_definition**）→ 不进任何 populator（`_WeatherPopulator` 实为 no-op，`resolver.py:1302-1303,1674-1698`）。bridge 链（`workflow_tasks.py:37-45`）：weather_bridge 需 `weather_request.workflow`（仅定时器按 `_meta.engine=weather` 组装，`workflow_timer_service.py:351-356`）→ 用户直提天气图层落到 **weather_engine fallback**（`weatherengine/service.py:70-72`：`layer_id in WEATHER_LAYER_SPECS` 即接管）。`BACKEND_WEATHER_WORKFLOW_ENABLED` 关闭时 bridge 全拒，全压 weather_engine。

### 4.3 两条路径的关系（非完全平行）

`/weather/tiles` 主路径（`weather_tile_routes.py:54-70` → `tile_service.get_tile`）与 DAG 路径**共用底层**：`tile_service.py:28,369` 同走 `fetch_gateway`；`:389` 与 DAG `grid_fetch` 节点共用 OpenMeteoClient 缓存。差异仅在编排层（REST 直渲染 vs WorkflowExecutor DAG）。

### 4.4 判定

**有意冗余（分层设计）：编辑器 DAG 演示 + 数据面瓦片主路径**。证据：seed 自述"仅用于编辑器联调 WeatherWorkflowService"（weather_wind_field_demo.json:16，`extra.purpose=weather_editor_demo`）；决策纪要（Docs/02-架构设计/工程决策纪要-配置瓦片与契约.md:12,20,23）定调天气正式入口 `/weather/tiles`；validator Rule 5（:198-212）warning 级防天气图层设 workflow_id。

**遗留成分**：weather_engine 作为 bridge fallback 未被 `BACKEND_LEGACY_WORKFLOW_HANDLERS_ENABLED` 约束，与决策纪要 §5"legacy 需开关"精神不完全一致。

**风险**：① seed 节点参数与 `WEATHER_LAYER_SPECS` 漂移（validator 只查 ID 不查参数）；② 编辑器跑 seed 的 DAG 渲染与瓦片热路径行为可能不一致（几何/缓存细节共用但编排不同）。

**建议方向**：保留 demo seed 维持标注；将 weather_engine fallback 纳入 legacy 开关或收紧 supports；为 weather seed 增加 `WEATHER_LAYER_SPECS` 参数一致性 CI 校验。

## 5. 总体结论与后续建议（按优先级）

1. **P2｜seed 解读单一真源化**（§1.3）：compiler 成为 seed 唯一解读方，resolver 停止自展平——根治"改字段约定另一处静默失配"（已有 3 处实锤史）。属重构，需专项窗口。
2. **P2｜workflow_engine 补测试**（§1.2）：天气通道生产内核零测试引用，任何改动都无回归保护。
3. **P2｜队列清单单一来源**（§2.3-1/2）：launch/constants.py 硬编码改为从 settings 生成 + 补 `task_default_queue` 兜底，清理 `"celery"` 死 fallback。
4. **P3｜materialize 脆弱点治理**（§3.3）：R1 palette 断裂、R2 静默丢弃、R4 中文 title（与 2026-08-23 上午 `17ceea8` 遗留问题直接相关）可先行小步修。
5. **P3｜weather_engine fallback 收口**（§4.4）：纳入 legacy 开关约束。
