## 二、Q1：多 EASE 网格操作能力

### 已统一的部分 ✅
**`grid_presets.py` 是唯一权威 preset 表**（15 个）：每个 preset 含 `crs/cols/rows/resolution/bounds/geographic_bounds/origin`，由 `_ease2()` 统一构建（对称角点防浮点越界），覆盖：
- EASE2 全球：9km(1624×3856)/36km/25km/3km
- EASE2 南北半球（LAEA，±9,000,000 网格域）
- EASE1（球体 25km）
- WGS84 全球

消费方 `raster_science.py`（`match_grid_preset(shape)` 形状匹配 + `needs_transpose` 转置检测——**MATLAB v7.3 HDF5 行列颠倒在此统一处理**）、`raster_timeseries.py` 也走 preset。

### 断裂的部分 ❌（绕过 preset 的平行实现）
1. **`overlay_recolor.py:29-48`**（昨夜我写的）：`_EASE_GLOBAL_9K_SHAPE=(1624,3856)` + `_EASE_EASE_UL` + `_EASE_GRID_9K_PIXEL_SIZE` 硬编码，**只支持 9km 一种**。25km/36km/3km/半球 EASE 源走 recolor 时几何错误（不会被识别，静默按通用路径产生几何偏差）。
2. **`overlay_registry.py:243`**：又一份 `_EASE_GRID_9K_PIXEL_SIZE = 9008.0552` + 各图层注释散落形状说明（:535,:930-931）。
3. **`Tools/export_overlay_assets.py:312-353`**：第三份 EASE 常数 + `_EASE_GRID_UL_BY_CRS`（含 EASE1/2.0 角点区分——**这份反而是最全的**，注释明确"1.0 与 2.0 角点不同，不可混用"）。

**前端**（crs-registry.ts 228 行 + crs-transformer.ts 271 行）：EASE 家族 proj4 串与后端 pyproj 对齐，前端坐标拾取/变换独立可用 ✅；渲染组件（overlay-image-bands/overlay-image-module）**不感知网格**——只消费 bounds+PNG，几何正确性完全依赖后端产出 ✅（这是好设计，保持）。

### 建议（P2，专项窗口）
- 把 `Tools/export_overlay_assets.py` 的 `_EASE_GRID_UL_BY_CRS`（EASE1/2 角点表）**下沉**到 `grid_presets.py`（加 `ul_corner` 字段），三处硬编码收敛为 preset 引用。
- `overlay_recolor._reproject_ease_to_mercator_linear` 改为按 preset 参数化（任意 EASE 分辨率可重投影），`_is_ease_global_9k` 形状判定改为 `match_grid_preset` 复用。
- `overlay_registry.py` 的常数删掉，引用 preset。

## 三、Q2：像元配准点（PixelIsArea vs PixelIsPoint）——当前完全隐式

### 现状
- **全仓 `AREA_OR_POINT` 零命中**（GeoTIFF 标准配准标签从未读取）。
- 所有链路统一隐式 **PixelIsArea 语义**：
  - `geo_math.pixel_center_axis`（双份）：`start + (i+0.5)*res`（边缘对齐 + 中心取值）——Area 语义
  - `spatial_aligner`：`from_bounds` + 像素中心目标坐标——Area 语义
  - `overlay_tile_service`/`raster_preview_service`：`from_bounds`——Area 语义
  - `weatherengine/field_mapping.py:501-514`：`(i+0.5)*res`——Area 语义
- **一致性是好的**（内部数据流不会互相错半像元），但有两个外部风险：
  1. **下载的 PixelIsPoint 数据**（如部分 SMAP L3 官方 GeoTIFF、GLDAS NetCDF 坐标变量是像元中心）：我们按 Area 解读 → **整体偏移半个像元**（9km 网格即 4.5km）。当前无检测、无校正。
  2. **算法结果回写**：若算法（MATLAB 系）输出坐标是"格点值在交点"（Point 语义，如再分析资料），同样偏半像元。

### 建议（P1.5，随下次数据链路改动落地）
1. **读取侧**：`UniversalDataReader`/`raster_science` 读 NetCDF/HDF 坐标变量时判定**坐标是边缘还是中心**（`axis[0]` 与 bounds 关系：中心坐标首点 = 边缘 + res/2 可判定），GeoTIFF 读 `AREA_OR_POINT` tag；结果挂在 `data_array.attrs['cell_registration'] = 'area'|'point'|'unknown'`。
2. **注册侧**：`raster_register` 写 bounds 时若源是 Point 语义 → **外扩半像元**（`west -= res/2` 等）转成 Area 语义对齐全链路。
3. **文档化**：在 grid_presets.py 模块头写明"本系统全链路 PixelIsArea；Point 源在读取/注册边界归一化"，防止未来各引擎各写各的。

这个改动能根治"有时候坐标点是左上角有可能是中间"的问题——不用每个引擎单独适配，**在读取边界归一化一次**即可。

## 四、Q3：代码复用审查

### 明确重复（应收敛）
| 重复项 | 位置 | 处置建议 |
|---|---|---|
| **geo_math 双份** | `app/services/geo_math.py` vs `algorithms/providers/Python/data_access/geo_math.py`（pixel_center_axis/nearly_equal 等逐字重复，backend 版多了 descending 参数） | 算法包**禁止 import service.***（既有铁律，跨进程部署），双份是历史妥协；建议**算法包为真源**（更底层），backend 侧 thin re-export 或测试对齐锁一致性（golden test 双实现同输入同输出） |
| **EASE 重投影双份** | `overlay_recolor._reproject_ease_to_mercator_linear`（昨夜我写，当时判断 Tools 顶层副作用不能 import）vs `Tools/export_overlay_assets.py` | 下沉为 `app/data_io/services/grid_reproject.py`（纯函数，rasterio+pyproj 依赖后端已有），Tools 与 overlay_recolor 共同引用 |
| **EASE 常数三处** | grid_presets / overlay_recolor / overlay_registry / Tools（实际四处） | 全部收敛 grid_presets（见 Q1） |
| **0.5 像素中心公式**散落 | geo_math ×2、weatherengine/field_mapping | field_mapping 的 `(i+0.5)*res` 改用 geo_math.pixel_center_axis（同进程可引用） |

### 合理的双栈（不动）
- **前后端 CRS 双栈**：前端 crs-registry/transformer（proj4，用于导入预检/拾取交互）vs 后端 pyproj（权威重投影）——**性能与职责分离，合理**；风险仅在 proj4 串与 pyproj 定义漂移 → 已有注释约定对齐，建议加 golden 用例（同一组角点前后端变换结果 <1e-6）锁一致。
- **GCJ/BD 转换双份**（gcj-bd.ts vs _gcj_bd.py）：同上合理。

### 复用良好的部分 ✅
- `colorize_array_to_rgba`（preview/tile/recolor 三路共用）
- `safe_import_child` 路径穿越收口
- `stable_import_layer_id` 产物 id 稳定化
- overlay 渲染组件不感知网格（bounds+PNG 契约）
