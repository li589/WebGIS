## 1. 问题一：网关间歇性 502（`host.docker.internal` 双栈陷阱）

### 1.1 现象

公网入口 `https://geoflow.cgdas.dpdns.org/` 偶发 502，失败率 **0.08%（53/65785）** ——
低到容易被当成"网络抖动"，但持续存在。

### 1.2 根因链

1. 网关是 Docker compose 项目（`Code/infra/gateway/docker-compose.yml`，容器 `cgda-gateway-nginx`），
   挂载 `./nginx.conf:/etc/nginx/nginx.conf:ro`，`extra_hosts: "host.docker.internal:host-gateway"`。
2. Docker Desktop（Windows）在容器 `/etc/hosts` 里给 `host.docker.internal` 写了**两条**记录：
   `192.168.65.254`（IPv4）与 `fdc4:f303:9324::254`（IPv6）。
3. nginx 的 `upstream` 用主机名时会把**所有解析结果**都放进上游池（默认 round-robin）。
4. 容器内 IPv6 那条**不可达**（`connect()` → Network unreachable）⇒ 轮询命中它就 502。
5. 概率 ≈ 1/2 的请求会先试 IPv6？不 —— nginx 对不可达上游会**立即尝试下一个**，所以表现为
   低频、无规律的偶发 502，而非 50% 失败。

### 1.3 修复（本仓库 `Code/infra/gateway/nginx.conf`）

```diff
     upstream cgda_fastapi {
-        server host.docker.internal:8000;
+        # 2026-09-24 修复间歇性 502：容器内 /etc/hosts 同时写了 IPv4/IPv6 两条记录，
+        # nginx 会把两条都放进上游池；IPv6 那条在容器里不可达，轮询到它就 502。
+        # 故直接写死 IPv4，避免坏节点进池。
+        # 若 Docker Desktop 重建网络导致 502 复现，先核对地址再替换：
+        #   docker exec cgda-gateway-nginx grep host.docker.internal /etc/hosts
+        server 192.168.65.254:8000;
         keepalive 16;
     }
```

### 1.4 验证

- `docker exec cgda-gateway-nginx grep -A3 "upstream cgda_fastapi" /etc/nginx/nginx.conf`
  → 已是新配置（容器随 09-27 重启重新加载）。
- 修复后 `:5175/health` 200，观察期内无 502。

### 1.5 权衡与复核

写死 IP 的代价：**Docker Desktop 重建网络后该地址可能变化**。因此：
- 注释里已留核对命令（见上）；若 502 复现，先核对地址再替换，不要盲目回退到主机名。
- 更彻底的替代方案（未采用，供后续参考）：upstream 只留一个 `server` 并加 `resolve`+
  `resolver 127.0.0.11`（需 nginx 官方镜像支持），或改用 `host-gateway` 的 IPv4 固定映射。
  在"改动最小、可立即生效"的前提下，写死 IPv4 是当前最优解。

## 2. 问题二：远端 `origin/dev` 引用损坏（`[ahead 84]` 假象）

### 2.1 现象

远端 `git status -sb` → `## dev...origin/dev [ahead 84]`，但 `git ls-remote origin` 证明
本地 HEAD `ca52cf96` **就是**远端 tip。`git push` 会误以为要推 84 个提交。

### 2.2 取证（三方对照，缺一不可）

| 位置 | 实测 | 说明 |
|---|---|---|
| `git for-each-ref refs/remotes` | `origin/dev = 0ef37db2`（**09-08 的旧提交**） | git **实际读到**的值 |
| `.git/packed-refs` | 含 `0ef37db2 refs/remotes/origin/dev`，mtime 停在 **09-18 13:27:50** | 旧条目**从未被更新** |
| `.git/refs/remotes/origin/dev`（loose） | **不存在**，且 `refs/remotes/origin/` **整个目录缺失** | 新值**没落盘** |
| `.git/logs/refs/remotes/origin/dev`（reflog） | **完好**，41 条，最后 `be8a5fe5→ca52cf96 update by push @ 09-24 12:18:21` | git **认为**自己更新成功 |
| `refs/remotes` 目录 | ctime=07-29（从未删除重建）、mtime=**09-24 12:18:21** | `origin/` 子目录消失于 **push 同一秒** |
| `refs/heads/dev`（loose） | 正常 `= ca52cf96` | 本地分支不受影响 |

关键反常点：reflog 里 **09-22 19:59 push 与 20:00:30 fetch 的 old 值都是同一个旧 sha
`0ef37db2`** —— 31 秒内刚写入的 loose 值就"丢了"，说明 loose ref 被反复删除。

### 2.3 机制

git 更新一个**已在 packed-refs 里的 ref** 时，应「写 loose 文件（loose 优先于 packed）」；
reflog 在 loose 落盘成功后写入。现在 reflog 有记录而 loose 缺失 ⇒ **loose 写入后又被删掉**。
后果：git 只能读到 packed-refs 里**陈旧的 09-08 值** ⇒ 一切基于 `origin/dev` 的判断
（ahead/behind、pull 的 ff 判断、IDE 的 Git 面板）全部失真。

### 2.4 已排除的嫌疑

| 嫌疑 | 排除依据 |
|---|---|
| fetch refspec 过窄（09-16 那次同类问题的根因） | `remote.origin.fetch = +refs/heads/*:refs/remotes/origin/*`，已是标准通配 |
| `git remote prune` / `fetch --prune` | `dev`/`main` 在 GitHub 上都存在，prune 无可删项 |
| git hook（`reference-transaction` 等） | `.git/hooks/` 只有 `pre-commit` / `commit-msg`（pre-commit 框架模板），无 ref 类钩子 |
| 计划任务清理 | 非微软计划任务里无可疑清理项（仅 360Zip/Adobe/Google/WPS 等更新器） |
| git 版本过旧 | git 2.55.0.windows.5（较新，暂无对应已知回归结论） |
| 本地分支损坏 | `refs/heads/dev` loose 正常，HEAD 工作完全正常 |

**未定案**：真正删除 loose ref 的进程尚未抓到（Defender 实际未启用，
机器上有 360 系/HEU KMS 等工具，均有嫌疑但无直接证据）。

### 2.5 修复（已执行，`_ops/fix_refs.py`）

1. 备份 `packed-refs` 与 reflog 到 `_ops/backup/packed-refs.bak.<ts>` / `reflog-origin-dev.bak.<ts>`；
2. `git fetch origin` —— 重建 loose（fetch 输出 `0ef37db2..ca52cf96 dev -> origin/dev`、
   `* [new branch] main -> origin/main`）；
3. `git pack-refs --all --prune` —— **规范化加固**：把当前正确值写进 packed-refs。
   此后**即便 loose 再次丢失，git 读到的也是正确值**，不会再退回 09-08；
4. 验证：`for-each-ref` → `origin/dev=ca52cf96`、`origin/main=a9b4f507`；
   `status -sb` → `## dev...origin/dev`（`[ahead 84]` 消失）。

### 2.6 复发监控与再排查指引

- **自查命令**（纳入日常巡检即可）：
  `git for-each-ref --format='%(refname)=%(objectname:short)' refs/remotes` 应与
  `git ls-remote origin` 一致。
- **若复发**（loose 再次消失）：先跑一次 `git fetch origin` 即可恢复；要抓凶手则：
  1. `git update-ref refs/remotes/origin/dev <tip>` 后立刻用 ProcMon（Sysinternals）
     过滤该路径，观察 Delete 事件的进程；
  2. 或对 `.git\refs\remotes` 启用对象访问审计（本地安全策略 → 审核对象访问 → 事件 4660/4663）；
  3. 候选嫌疑：360 系工具的"清理/文件防护"、杀软实时扫描、第三方 IDE 的 git 集成。
- **运维约定**：远端任何 `push/fetch` 之后，顺手 `git status -sb` 看一眼
  ahead/behind 是否合理；出现夸张数字（如 ahead 84）先查 `for-each-ref` 再动手。

## 3. 问题三：三端同步方案

### 3.1 拓扑与通道约束

| 端 | git 通道 | 约束 |
|---|---|---|
| GitHub | — | 真源 |
| 远端 Win10 | **可直连** GitHub（fetch + push 均可） | 唯一能直接 push 的端 |
| 本机开发机 | **被墙**（`github.com:443` 重置，fetch/push 均不可用） | 只能走两条旁路：① GitHub Git Data API（push 用）；② **SSH 隧道内传 bundle（本次同步用）** |

### 3.2 方案：远端为源 → bundle 过隧道 → 本机 ff

1. 远端完成待同步提交（nginx 修复 + 本文档）并 `git push origin dev`；
2. 远端 `git bundle create <file> 3db3ef3d..dev`（只含本机缺失的增量，体积小）；
3. bundle 经既有 SSH 隧道以 base64 回传本机（复用 `pull_files.py` 通道）；
4. 本机 `git fetch <bundle> dev:ref/bundle-tmp` → `git merge --ff-only` → 校验 SHA 与远端**逐字一致**；
5. 三端验收：`ls-remote`（GitHub）/ 本机 `rev-parse HEAD` / 远端 `rev-parse HEAD` 三者相等。

> 选 bundle 而非 API 拉对象的原因：bundle 是**标准 git 对象流**，SHA 天然逐字一致、
> 无需手写"API 逐对象下载"脚本；SSH 通道此前已稳定传输过 1.2 MB 级文件。

### 3.3 验收标准

- [ ] GitHub `dev` = 远端 `dev` = 本机 `dev`（同一 SHA）
- [ ] 三端 `git status` 均干净（除本机/远端各自的本地 gitignored 配置）
- [ ] 远端 `for-each-ref refs/remotes` 与 `ls-remote` 一致（引用健康）
- [ ] 公网 `:5175/health`、`:8000/health` 均 200
