## 1. 部署形态：已决策（全量容器化）

### 1.1 决策基线（2026-09-16 用户确认）

| 项 | 决策 |
|---|---|
| 目标形态 | **全量容器化**：后端（FastAPI / Worker / Beat）与前端网关全部进容器；Redis / MinIO / Open-Meteo 沿用官方镜像 |
| 目标 OS | **Linux（CentOS / RHEL 系，Debian / Ubuntu 系）** 与 **Windows 10 及以上** |
| 数据盘 | **本地盘**（宿主机挂载，容器经 bind mount 挂入；Windows 注意盘符写法，见 §12.4） |
| 网络 | 目标机**可访问网络**（拉镜像 / 装依赖 / 访问 GEE 与上游数据源） |

### 1.2 形态对照（决策依据，保留以便复盘）

仓库此前**没有**任何形态的完整生产工件（见 §10-G1）：后端/前端未容器化，`Env/` 被 gitignore。三形态对照如下：

| 形态 | 适用场景 | 仓库现状支撑 | 需补工作 | 主要风险 |
|---|---|---|---|---|
| **A. Linux 服务器裸机** | 课题组/机构内网长期运行 | 高：`start.sh` 会找 `Env/Python312/bin/python`，`launch.py` 全命令跨平台；4 个 compose 提供基础设施 | systemd 单元或守护脚本、`Env` 环境构建脚本、TLS 终结方案 | 环境靠手工复现，跨机一致性弱 |
| **B. 全量容器化** ✅ **已采用** | 需可复现交付、多台部署、后续扩容 | 低：**全仓无 Dockerfile**（`find` 确认）；Nginx/Redis/MinIO/Open-Meteo 已是官方镜像 | backend/frontend Dockerfile、生产 compose、卷与数据盘挂载策略、镜像构建与分发（**§12 已给草案**） | 工作量大；科学库（rasterio/GDAL/numba）镜像体积与构建时长 |
| **C. Windows 单机** | 演示、单机交付、开发机兼作交付机 | 高：`start.bat` 已强制 `Env\Python312`；端口/管理员约束已成文 | 开机自启、Docker Desktop 依赖固化、安全软件白名单 | 依赖 Docker Desktop 与 WSL，历史上出过 WSL 数据目录断链、WinNAT 吞端口（见 §9） |

### 1.3 形态切换带来的六个变化

1. **宿主机只需 Docker**：不再需要 Node / Python 运行时（`Env/` 只服务开发机）。
2. **后端进程进容器**：网关反代目标由 `host.docker.internal:8000` 改为**服务名**（如 `backend:8000`），`nginx.conf` 需出容器化变体。
3. **数据盘经 bind mount 挂入**：Linux 直接 `/data/...`；Windows 用 `D:/...`（**不要**用 MSYS 风格 `/d/...`）。见 §12.4。
4. **`restart: unless-stopped` 取代 systemd**：另需把 Docker 服务本身设为开机自启（§12.5）。
5. **`launch.py` 退出交付链**：降级为开发/排障工具；生产启停由 compose 承担。
6. **镜像构建成为新工件**：§10-G1 由 P1 升为 **P0 主线**，§12 给出可评审的 Dockerfile 与编排草案。

### 1.4 仍未决 U2（不阻塞开工，开工前定即可）

- **镜像分发方式**：目标机本地构建 / 私有 registry / `docker save` + `docker load`（完全隔离环境）；
- **是否需要对外 TLS**：仅在机构内网使用时可由内网边界承担；出网或跨机构交付则需补反代与证书（§5-B6、§10-G3）；
- **数据盘文件系统**：Linux 建议 xfs/ext4；Windows 为 NTFS 卷。注意两者的 bind mount 写法差异与权限模型（Linux 容器内 UID/GID 映射，§12.4）。

## 2. 拓扑与端口契约

对外**只有一个入口**：Nginx Gateway `:5175`。其余端口除 `:5175` 外均绑回环。

| 服务 | 监听 | 载体 | 配置出处 | 对外 |
|---|---|---|---|---|
| Nginx Gateway | `5175` | 容器 `cgda-gateway-nginx` | `Code/infra/gateway/docker-compose.yml`、`nginx.conf` | ⚠️ 绑 `0.0.0.0`（`"5175:5175"`），局域网可达；明文 HTTP |
| FastAPI | `127.0.0.1:8000` | 宿主机进程（`start_fastapi.py`→uvicorn） | `Code/backend/.env`（HOST/PORT） | 回环 |
| Vite（仅 `--vite`） | `127.0.0.1:5174` | 宿主机进程 | `launch/constants.py` | 回环 |
| Redis | `127.0.0.1:16379` | 容器 `cgda-redis` | `Code/backend/docker-compose.yml` | 回环 |
| MinIO API / Console | `127.0.0.1:9100` / `9101` | 容器 `cgda-minio` | 同上 | 回环 |
| Open-Meteo API | `127.0.0.1:8080` | 容器 `cgda-open-meteo` | `OPEN_METEO_HOST_PORT` | 回环 |

两条 compose 栈，**不可混用 project 名**：

| 栈 | 路径 | project | 内容 |
|---|---|---|---|
| 运行栈 | `Code/backend/docker-compose.yml` | `-p backend` | Redis / MinIO(+init) / `cgda-open-meteo`（长期运行） |
| 数据栈 | `Code/infra/data-sync/docker-compose.yml` | `-p data-sync` | 一次性 `run --rm` 同步任务（当前仅 `open-meteo-sync`） |

两栈共享 named volume `backend_open-meteo-data`（`external: true`），落在 Docker Desktop VHDX 内。

### 2.1 目标态（容器化）服务布局

| 服务 | 容器 | 对外暴露 | 说明 |
|---|---|---|---|
| `gateway` | `cgda-gateway-nginx` | `5175:5175` | 静态 dist + 反代 **`backend:8000`**（服务名，不再是 `host.docker.internal`） |
| `backend` | FastAPI（uvicorn） | 不对外（仅 compose 网络） | 生产 `BACKEND_RELOAD=false`（B6）；`BACKEND_FASTAPI_WORKERS` 生产设 2+ |
| `worker` | Celery（7 队列 / 每队列 N 实例） | 不对外 | Linux 建议 `BACKEND_CELERY_WORKER_POOL=prefork`（Windows 为 solo 兜底） |
| `beat` | Celery Beat | 不对外 | **单副本**；多副本会重复触发定时任务 |
| `redis` / `minio` / `open-meteo` | 官方镜像（沿用现状） | 不对外 | 生产**不应**再把 16379 / 9100 / 9101 / 8080 发布到宿主机 |

三条硬性共享关系（违反即出现"任务找不到产物/状态"类故障）：

1. `backend` 与 `worker` 必须共享同一 `BACKEND_DATA_ROOT` / `BACKEND_OUTPUT_ROOT` / `BACKEND_RUNTIME_ROOT`（同一 bind mount + 同一 SQLite 文件）；
2. `beat` 与 `worker` 必须共享同一 `redis` 与同一 `workflow_state.sqlite3`；
3. `open-meteo`（API）与数据面同步任务必须共享同一 named volume（§5-A5）。

网关内部语义（改 `nginx.conf` 前必读）：`index.html` 与 `/` 为 `no-store`；`/assets/*` 与 `/cesium/` 缺失**必须真 404**（禁 SPA 回退）；API 反代**不开** `proxy_intercept_errors`，应用错误 JSON（`request_id`/`error_code`/`Retry-After`）原样透传；含 `add_header` 的 location 必须重新 `include` 安全头片段。依据：`Code/infra/gateway/nginx.conf`、`Code/infra/gateway/README.md`。

## 3. 外置依赖与前置条件

### 3.1 目标态（容器化）宿主机只需三样

| 项 | 要求 | 备注 |
|---|---|---|
| 容器运行时 | Docker Engine（Linux）/ Docker Desktop 或 WSL2 后端（Windows 10+） | Windows 上 Docker 与执行终端须**管理员**（§5-A1） |
| 本地数据盘 | 已挂载、可读写、容量足够；`BACKEND_DATA_ROOT` / `BACKEND_OUTPUT_ROOT` 对应目录**必须已存在**（不会自动创建根） | `配置文件治理说明.md §3.1` |
| 出网能力 | 拉取基础镜像、Python/Node 依赖、访问 GEE 与上游数据源 | 内网需配 registry 镜像源或离线 `docker save/load`（§1.4-U2） |

**构建期**才需要 Node 22 与 Python 3.12：两者都进镜像（§12 的多阶段构建），宿主机不需要安装。
`Env/Python312` 从此只服务开发机与 `launch.py` 排障链。

### 3.2 OS 差异矩阵

| 维度 | CentOS / RHEL 系 | Debian / Ubuntu 系 | Windows 10+ |
|---|---|---|---|
| 容器运行时安装 | `dnf install docker-ce`（需配置官方源） | `apt install docker-ce` | Docker Desktop（须开启 WSL2 后端） |
| 开机自启 | `systemctl enable --now docker` | 同左 | Docker Desktop 设置 → General → Start Docker Desktop when you sign in |
| SELinux / AppArmor | SELinux 常为 enforcing → bind mount 需 **`:z`/`:Z`** 或 `--security-opt label=disable` | AppArmor 一般放行 | 不适用 |
| 数据盘 bind mount | `/data/geo:/data/geo` | 同左 | **`D:/geo:/data/geo`**（禁 MSYS 风格 `/d/...`，会挂载失败） |
| 文件权限 | 容器内 UID/GID 需与数据盘属主一致（§12.4） | 同左 | NTFS 无 POSIX 权限，SQLite 并发写入需注意性能 |
| 端口保留段坑 | 无（Linux） | 无 | **WinNAT 动态排除段**吞端口（§5-A3），本项目已躲 16379/9100/8080 |

### 3.3 镜像内需要预置的系统工具

| 工具 | 用途 | 缺失后果 |
|---|---|---|
| `unrar`（Linux 包 / Windows `UnRAR.exe`） | archive 导入（zip/rar/7z） | 归档类导入失败 |
| `mod_spatialite`（`libsqlite3-mod-spatialite`） | 空间叠加层 | 自动降级（`BACKEND_SPATIALITE_ENABLED=true` 但扩展不可用） |
| GDAL | FY 提取链 | FY 相关算法不可用 |

数据盘目录结构模板：`Docs/03-规范协议/当前数据源与产出一览.md`。

## 4. 配置分层与生效边界

四层模型（谁可改 / 存哪 / 怎么生效）以 `Docs/03-规范协议/配置文件治理说明.md` 为单一真源，摘要如下：

| 层 | 存储 | 修改入口 | 生效方式 |
|---|---|---|---|
| 部署/数据配置 | `Code/backend/deployment.config.json`（真源）+ `.env`（镜像） | 前端 `/deployment`（仅 admin） | 重启后端进程组；docker 组键需全量 `restart` |
| 底层引导配置 | `Code/backend/.env` | 配置中心镜像 / 运维手改 | 重启后端进程组 |
| 运行时热载 | SQLite（DB overlay） | 既有设置面板 | 热载，无需重启 |
| 运行时调优（19 键） | SQLite `runtime_config` | 设置 → 通用 | FastAPI 即时；**worker 需新世代** |

**加载链**：`load_dotenv(.env)` → `deployment.config.json` 解析 + schema 校验 → 逐键覆盖 `os.environ`（**json 优先于 .env**）→ `Settings()` 冻结。FastAPI / Worker / Beat 经 `import app.core.config` 触发同一链路。json 解析或 schema 失败 → **fail-closed 拒启**，错误含 `.bak.1/.2/.3` 恢复指引。

**漂移检测**：`GET /config/deployment` 对每键返回 `runtime_value` / `env_value` / `config_value` + `source`；任一 `pending` → 顶层 `pending_restart=true`（前端显示"待重启生效"徽章）。**运维手改 `.env` 会立刻被此机制暴露。**

**改什么 → 怎么生效**（左列为**开发机/裸机**；右列为**形态 B 容器化**）：

| 改了什么 | 裸机 / 开发机 | 容器化（形态 B） |
|---|---|---|
| 任何 `.py`、`.env`、`deployment.config.json` 的 backend 组键、数据根 | `launch.py restart backend`（默认清 `__pycache__`） | `docker compose restart backend worker-* beat` |
| 前端源码 | `--vite` 开发；静态剖面须 `npm run build` 或 `launch.py restart --rebuild-frontend` | 重建 `cgda-web` 镜像 → `docker compose up -d gateway` |
| `nginx.conf` / 维护开关 | `launch.py reload gateway`（`nginx -t` + reload，不重建容器） | `docker compose exec gateway nginx -s reload`（维护开关经挂载即时生效） |
| docker 组键（MinIO 凭据、`OPEN_METEO_*`） | `launch.py restart`（全量） | 改 `.env` → `docker compose up -d`（重建受影响容器） |

### C. 数据面

第三方镜像沿用仓库既有的 **tag/digest pin** 做法（供应链加固约定，见 `Code/backend/docker-compose.yml` 注释）；自建镜像建议同样 pin 基础镜像 digest。

### 12.2 镜像目录布局（硬约束）

**必须保持 `Code/` 的兄弟目录结构**，否则后端启动即失败：

| 证据 | 含义 |
|---|---|
| `Code/backend/start_fastapi.py:18-24`、`start_celery_worker.py:6-13` | 启动脚本把 `backend_root.parent`（即 `Code/`）插入 `sys.path` |
| `Code/backend/app/core/config.py:42-44` | `DEFAULT_PYTHON_PROVIDER_ROOT = BACKEND_ROOT.parent / "algorithms" / "providers" / "Python"` |

⇒ 镜像内布局固定为 `/srv/Code/{backend,algorithms,shared}`，工作目录 `/srv/Code/backend`。
**不要**把 backend 单独 COPY 到 `/app` —— 兄弟目录缺失会导致算法 provider 解析失败。

### 12.4 数据盘与卷（bind mount）

| 宿主机 | 容器内 | 读/写 | 说明 |
|---|---|---|---|
| 本地数据盘（`<DATA_ROOT>`） | `/data/geo` | 读写 | 算法数据；**目录必须已存在** |
| `<OUTPUT_ROOT>` | `/data/geo/ProjectOutput` | 读写 | 产物根 |
| `<DATA_ROOT>/_runtime` | `/data/geo/_runtime` | 读写 | runtime 派生根（workflow_state / logs / artifacts / cache） |
| `Code/backend/.env` | `/srv/Code/backend/.env` | 只读 | 引导配置（含密钥），用 `:ro` |
| `Code/backend/deployment.config.json` | 同路径 | 只读 | 部署配置真源；**经配置中心写入时需可写**，见下 |
| `Code/infra/gateway/maintenance/` | `/etc/nginx/maintenance` | 读写 | 维护开关 `on` 需运行时可变 |
| 各容器 `.data`（可选） | `/srv/Code/backend/.data` | 读写 | **beat 调度库**落在 `backend/.data/celerybeat-schedule`（`start_celery_beat.py`），需持久卷 |

要点与坑：

1. **`deployment.config.json` 的读写矛盾**：配置中心 `PUT /config/deployment` 要求该文件可写。
   容器化后有两个选择——(a) 挂载为可写并接受"配置写入容器内挂载点"；(b) 禁用容器内的配置中心写入，
   改为宿主机侧维护后重启容器。**建议 (a)**，与现状行为一致。
2. **Linux UID/GID 对齐**：数据盘属主须与容器内 `cgda` 用户一致，否则产物写不进去。
   构建时 `--build-arg CGDA_UID=$(id -u)`，或运行时 `user: "$(id -u):$(id -g)"`。
3. **SELinux（CentOS/RHEL）**：bind mount 需加 `:z` / `:Z`，否则容器内读取被拒。
4. **Windows bind mount**：写 `D:/geo:/data/geo`；**不要**用 `/d/geo`（挂载会失败）。
5. **SQLite 在 Windows 挂载卷上的锁与性能**：`workflow_state.sqlite3` 是并发写入热文件。
   Windows 上建议把 runtime/state 放 **named volume**（容器内），数据盘只放算法数据与产物；
   Linux 本地盘可直接 bind mount。
6. **不要**把 Open-Meteo 数据改为 bind mount（§5-A5）。

### 12.5 生产编排草案（`compose.prod.yml`）

> ⟂ **已落地**：`Code/backend/compose.prod.yml`（**13 个服务**：backend + worker-×7 + beat + gateway，
> 与基础设施 `docker-compose.yml` 合并使用）。与下面草案相比的**必要偏差**——
> 每一条都对应一个会真实爆炸的故障，改动前请先读 `Win10-交接部署与三态启动方案.md` §3.2.1：

| 偏差 | 原因 |
|---|---|
| 每个服务显式 `CGDA_LOG_FILE_ROLE`（`fastapi` / `worker-<name>` / `beat`） | 9 容器共享同一 `BACKEND_LOG_DIR`（派生自数据根），不设就退回**同一个** `backend.log`，多进程抢 `RotatingFileHandler`（`app/core/logging.py:57-58` 已为裸机态修过此 bug） |
| 增 `BACKEND_OPEN_METEO_SYNC_ENABLED: "false"` | `open_meteo_sync_executor.py:316` 用 subprocess 调 `docker compose`，容器内无 CLI/socket；而该开关**代码默认 true** ⇒ Beat 每 6 小时必报错。同步改在宿主执行 |
| 增 `BACKEND_DATA_ROOT` / `BACKEND_OUTPUT_ROOT` / `BACKEND_CELERY_WORKER_POOL` 显式值 | 数据根必须指向挂载点；pool 显式 `prefork` 避免被 `.env` 里的 Windows 兜底值 `solo` 带偏 |

| `environment` 用第二个锚点 `x-backend-env` + 每服务重复 `<<: *backend-env` | YAML 合并键**不深合并**：服务级一旦出现 `environment:` 就整体替换锚点 |

### 12.9 改码工作流：镜像化之后「改代码」会不会变麻烦？

**先给结论**：不会变"不能改"，变的是**「改完怎么生效」**。

镜像化的本质，是把"运行版本"从"宿主工作目录的当前状态"换成"不可变的镜像 sha"。由此产生两个副作用，也就是"变麻烦"的真正来源：

1. 改完源码**不会自动生效**——进程读的是镜像内的副本，不是宿主工作目录；
2. 生效需要**重新构建 + 重建容器**，链路比裸机的 `launch.py restart backend` 长。

但对**开发机**，这可以用 bind mount 完全消除；对**交付机**，"必须重新构建才能改"恰恰是想要的性质——可回滚、可审计、防现场手改。

**两种模式，务必别混用**

| 维度 | 交付态（生产） | 开发态（改码） |
|---|---|---|
| 源码来源 | 构建期 `COPY` 进镜像，镜像内是**只读副本** | `bind mount` 宿主 `Code/` → 容器 `/srv/Code` |
| 改后端 `.py` | `docker build` → `docker compose up -d backend` | 容器内 `--reload` 自动重载；或 `docker compose restart backend` |
| 改前端 `.vue/.ts` | `npm run build` → 重建 `cgda-web` 镜像 | Vite dev server（HMR），不重建镜像 |
| `.env` / 数据根 | `docker compose restart backend worker-* beat` | 同左（bind mount 不影响 env 读取） |
| 版本标记 | 镜像 tag = git sha，**运行版本可追溯** | 无意义（就是工作区状态） |
| 回滚 | `CGDA_TAG=<old-shas> docker compose up -d` | `git checkout` |
| 谁用 | 交付机、验收环境 | 开发机、联调机 |

**四类改动 → 生效代价**

| 改了什么 | 需要重建镜像？ | 命令 | 说明 |
|---|---|---|---|
| 后端 / 算法 `.py` | 交付态：是<br>开发态：否 | 交付 `docker build … && docker compose up -d backend worker-* beat` | **worker 不吃 reload**；改 worker 代码必须重启 worker 进程 |
| 前端 `.vue` / `.ts` | 交付态：是<br>开发态：否 | 交付重建 `cgda-web` | 开发态走 Vite HMR |
| 配置（DB overlay / runtime 键） | 否 | 设置面板 / `POST /config/*` | 热载；runtime 键对已运行 worker 需新世代（§4、D5） |
| 依赖（`requirements.txt` / `package.json`） | **是**（必然） | `docker build`（指定层） | 唯一"每次都要等"的改动；把科学库层前置可获得缓存 |
| 镜像内系统工具（`unrar` / GDAL） | 是 | 改 Dockerfile 后重建 | 见 §3.3 |

**开发态落地（草案 `compose.override.dev.yml`）**

```yaml
# 与生产编排叠加使用：
# docker compose -p cgda -f Code/infra/gateway/compose.prod.yml -f compose.override.dev.yml up -d
services:
  backend:
    volumes:
      - ./Code:/srv/Code                 # 源码实时可见，覆盖镜像内副本
      - ${CGDA_DATA_ROOT}:/data          # 数据盘（与 §12.4 同款）
    environment:
      BACKEND_ENV: development           # ← 必须；否则热载被生产守卫关闭（见坑 1）
      BACKEND_RELOAD: "true"
    command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]
  worker-standard:
    volumes:
      - ./Code:/srv/Code
  gateway:
    volumes:
      - ./Code/infra/gateway/nginx.conf:/etc/nginx/nginx.conf:ro
```

**三个必须知道的坑**

1. ⬛ **热载会被生产守卫关掉**：`BACKEND_RELOAD` 代码默认 `true`（`config.py:251`），但 `start_fastapi.py:32-40`
   在**非 development** 环境强制关闭（硬约束 B6）⇒ 容器里想开 `--reload` 就必须 `BACKEND_ENV=development`，
   而 B1 又要求生产**不得**为 development。
   ⇒ **开发态与交付态必须用不同 compose 文件（或不同 `.env`），不能一套配置通吃**。这是本方案最容易踩的一处。
2. **worker 不热载**：Celery 进程不监听文件变化，改 worker 代码必须 `docker compose restart worker-*`。
3. **不要给 Open-Meteo volume 加 bind mount**：硬约束 A5（Windows 上 bind mount 该卷 → errno 95 / 数据错位）。
   数据盘的 bind mount（§12.4）是允许的，两者勿混。

**Windows 额外提示**：Docker Desktop 跨文件系统的 bind mount（尤其挂到 `I:\` 等非系统盘）I/O 明显慢于 Linux。
若开发机就是 Windows，改码联调优先用**裸机 `launch.py` + `Env/Python312`**（§7），**容器只用于验证交付态**；
确需容器内改码时再挂载，且只挂 `Code/`，不要把 `Env/`、数据集大目录一并挂入。

**给交付方的操作建议**：交付机默认**只给镜像**（`docker save` / 私有 registry），不给源码，现场自然"不方便改"——
这是交付边界，不是缺陷。若合同要求现场可改码，则必须同时交付：**源码 + `Dockerfile` + registry 或基础镜像**（§12.6），
否则现场没有重建镜像的手段。
