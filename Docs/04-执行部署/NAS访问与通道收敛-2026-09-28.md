# NAS 访问与通道收敛方案（2026-09-28）

> 结论：NAS（群晖）暴露的可用协议只有 **DSM 网页（HTTP 5000 / HTTPS 5001）** 与 **SMB（445）**，
> NAS 自身 SSH（22）/ Synology Drive（6690）均未开放。远端 Win10 已部署 CGDA，**filebrowser 中转通道
> （`nasfile.*`）与 NAS 网页隧道（`nasweb.*`）不再需要**：远端侧直接走局域网地址，本机侧用
> **SSH 别名 `nas-lab`**（LocalForward）访问 DSM 网页，文件传输走远端 `Z:`（SMB）。
> 本文**不含任何口令**；凭据只在各机本地维护（见 §4 纪律）。

## 0. 结论速查

| 需求 | 路径 | 说明 |
|---|---|---|
| 本机浏览器开 DSM | `ssh nas-lab`（保持连接）→ `http://127.0.0.1:15000`（HTTPS `:15001`） | 别名定义见 `~/.ssh/config`，**未硬编码任何凭据** |
| 文件读写 | 远端 Win10 `Z:` → `\\222.200.176.12\group_nas`（SMB 445） | 经 `ssh win11-lab` 操作；本机 SMB 不转发（§3.2） |
| 脚本化 DSM API | `http://222.200.176.12:5000/webapi/auth.cgi`（`SYNO.API.Auth` v6，path=`entry.cgi`） | 注意会话类型限制（§4） |
| 旧隧道域名 | `nasfile` / `nasweb` | **已退役**，见 §5 |

## 1. 背景与决策

- 早期：远端 Win10 通过 filebrowser 挂 NAS 的 `Z:`，再经 Cloudflare 隧道 `b13d485e` 对外提供
  `nasweb.*`（NAS 网页）与 `nasfile.*`（filebrowser）。
- 现在：项目已部署在远端 Win10 并常态化经 `ssh win11-lab` 运维，**多一层 filebrowser 只是多一个
  口令暴露面与一条会死的隧道**。决定收敛为两条通道：SSH（运维 + 端口转发）与远端 SMB 盘符。

## 2. 协议面探测结果（2026-09-28，自远端实测）

| 端口 | 服务 | 状态 |
|---|---|---|
| 5000 | DSM HTTP（`/webapi/`，API path=`entry.cgi`） | OPEN |
| 5001 | DSM HTTPS（自签证书，需跳过校验） | OPEN |
| 445 | SMB（共享 `\\222.200.176.12\group_nas`，远端映射为 `Z:`） | OPEN |
| 22 | SSH/SFTP | **closed** |
| 6690 | Synology Drive | closed |
| 137 | NetBIOS | closed |

⇒ 「用什么协议连」的答案：**网页管理走 DSM（5000/5001），文件走 SMB（445）**；没有第三种（SSH/SFTP/Drive 都关着）。

## 3. 访问方式

### 3.1 本机 → DSM 网页（`nas-lab` 别名）

`C:\Users\<用户>\.ssh\config` 已新增（与 `win11-lab` 同一条 Cloudflare 隧道，仅多两行转发）：

```
Host nas-lab
    HostName win11ssh.personaltunnel.dpdns.org
    User qiujianxiu
    ProxyCommand cloudflared access ssh --hostname %h
    LocalForward 127.0.0.1:15000 222.200.176.12:5000
    LocalForward 127.0.0.1:15001 222.200.176.12:5001
```

用法：`ssh nas-lab`（提示输入远端 Win10 口令；**连接保持期间**转发生效），浏览器开
`http://127.0.0.1:15000`。已实测两端口均返回 200。口令不写入配置文件——这就是「拒绝参数硬植入」的落点：
转发规则是拓扑事实可以入库，凭据永远只在人手上。

### 3.2 文件读写：SMB 不做本机转发

Windows SMB 客户端硬性走 445 且本机 445 被系统占用（无法 LocalForward），所以文件操作一律经
远端执行：`ssh win11-lab` 后用 `Z:\...`（或 `\\222.200.176.12\group_nas\...`）。这也与"数据根在远端
`E:\Project\CGDA\Data`"的现状一致——数据不落本机。

### 3.3 脚本化 API（供后续自动化参考）

`GET http://222.200.176.12:5000/webapi/auth.cgi?api=SYNO.API.Auth&version=6&method=login&...`
从**远端机**发起（该 IP 属远端局域网）。脚本示例见 `_ops\nas_probe.py`（仓库外，含 logout 清理）。

## 4. 账号情况与凭据纪律（口令一律不写入本文）

| 账号 | 验证结论（2026-09-28 实测） | 备注 |
|---|---|---|
| `wangxy` | ✅ 可用。用 `session=FileStation` 经 HTTPS 5001 登录成功（拿 sid 后已 logout） | 用其它 session 名会返回 **402（Permission denied）**——这是**应用受限**而非口令错误，与 400（口令错/无此账号）要区分开 |
| `Teacher` | ❌ 两个候选口令均 400；远端全盘取证无落痕（凭据管理器空、无 filebrowser 残留、计划任务无关） | 找回路径只剩 **DSM 管理员重置**。若记得更多候选，每账号**至多再试 2 次**（DSM 有自动封锁） |
| `admin`（原 filebrowser 只读口令） | ❌ 对 DSM 返回 400 | 属 filebrowser 专用凭据，随 filebrowser 退役 |

**凭据纪律**：口令不进 git、不进文档、不进 `~/.ssh/config`；探测脚本里只出现口令的 sha256 前 8 位指纹
用于报告比对；本地一次性密码文件用完即删。

## 5. 旧通道退役状态

- `b13d485e` 隧道（承载 win11ssh/win11file/nasfile）已于 2026-09-27 失效且**token 本地无副本**；
  SSH 入口现由 `win11-lab` 等价域名独立承载（同一条 Cloudflare 隧道配置域，两别名指向同一 `HostName`）。
- Cloudflare 侧 `nasweb.*` / `nasfile.*` 映射仍在配置里但已无用途；彻底清理需在 Cloudflare Zero Trust
  控制台操作（本地无 b13d token，无法命令行处理），非紧急。

## 6. 运维速查

| 症状 | 排查 |
|---|---|
| `ssh nas-lab` 连不上 | 先验证 `ssh win11-lab` 是否存活（Cloudflare 530=隧道死，502=源站死）；两别名共用一条隧道 |
| 15000/15001 被占 | `netstat -ano | findstr :15000`，改 config 里的本地端口即可（远端侧不用动） |
| DSM 登录 402 | 换 `session=FileStation` 或走 DSM 网页登录；402 是应用受限，不是口令错 |
| `Z:` 不可用 | 远端 `net use Z:` 复查映射；重新 `net use Z: \\222.200.176.12\group_nas <口令 /user:...>` |
