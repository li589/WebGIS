## 2. 数据落位方案（关键决策）

这是整个规划里唯一需要你拍板的技术方向。四条路线对比：

| 方案 | 通道 | 预估耗时 | 优点 | 风险 / 代价 |
|---|---|---|---|---|
| **A1** 临时放行远端入站 445 + SMB 拉取 | 同网段 1 Gbps | ~2 h @100 MB/s | 最快、可断点续传（robocopy `/Z`） | 需临时改远端防火墙 + 建共享，事后须回收 |
| **A2** 临时放行远端入站 22 + scp/rsync | 同网段 1 Gbps | ~2.2 h | 不必建 SMB 共享 | 同样需临时防火墙规则；rsync 在 Windows 需额外组件 |
| **B** 复用 `F:\SM` + `F:\SMAP_L4` | 本机 | 0 | 零传输、立刻可用 | **只覆盖 SM / SMAP 两类**，缺其余十余类，Dataset 不完整 |
| **C** 经现有隧道直传 | Cloudflare 隧道 | 10 h+ | 不动防火墙 | 隧道承载海量数据易断、拖慢交互；不推荐 |
| **D** 先落**最小可跑子集**，全量后补 | 视 A/B | 分钟级 | 今天即可跑通冒烟 | 需先圈定子集范围 |

**建议路径：D → A1**
1. 先用 D 落一个最小子集（例如 `Meteorological` + `ProjectOutput` 骨架 + 一个 Hazards 样例），把后端 / 前端 / 隧道链路整体跑通；
2. 再在后台用 A1 做 760 GB 全量同步，不阻塞联调。

## 4. 再开发闭环

```
远端编辑代码 (codegraph)  →  git commit  →  git push origin  →  本地 git pull 校验
        ↑                                                              │
        └──────────────────  反向同步同样可行  ──────────────────────────┘
```

- **主方向**：在远端工作副本上改 → 提交 → 推送 → 本机拉取并跑 CI。
