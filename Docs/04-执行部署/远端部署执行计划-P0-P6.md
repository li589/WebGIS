### 2.2 非交互 SSH 会话下 Docker 凭据助手必失败

报错：
```
error getting credentials - err: exit status 1, out: `A specified logon session does not exist.`
```
原因：SSH 是**网络登录**会话，无交互登录会话 ⇒ `docker-credential-desktop` 访问 Windows 凭据管理器失败。
且 Docker Desktop 的 CLI 在 config **未指定 `credsStore` 时会默认用 `desktop`**（所以 `--config` 指向干净配置也照样报错）。

**处置**：仓库外建匿名凭据助手 + 专用 `DOCKER_CONFIG`（两者必须同时生效）：

| 文件 | 作用 |
|---|---|
| `E:\Project\CGDA\_ops\docker-cred\docker-credential-cgdaanon.cmd` | `get` 回 `{"Username":"","Secret":""}` ⇒ 视为无凭据 → 匿名拉取 |
| `E:\Project\CGDA\_ops\docker-config\config.json` | `{"auths":{},"credsStore":"cgdaanon"}` |

> **踩坑**：助手 `get` 若**什么都不输出**（exit 0），docker 会报 `EOF`；必须回**合法 JSON**。

### 2.3 服务进程不能靠 SSH 会话存活 ⇒ 用计划任务

`launch.py` 用 `CREATE_NO_WINDOW` 拉起子进程，**SSH 会话一断就被回收**（实测：detached 的 `Start-Process`/`cmd` 全部秒退）。
**处置**：用 Windows 计划任务把启动动作"脱离会话"：

| 计划任务 | 触发 | 幂等守卫 |
|---|---|---|
| `CGDA-Stack` | ONLOGON | 若 `:5175` 已在监听则直接退出 |
| `CGDA-Tunnel` | ONLOGON | 若已有**含同一 token** 的 `cloudflared.exe` 则直接退出 |

手工拉起：`schtasks /Run /TN CGDA-Stack` / `schtasks /Run /TN CGDA-Tunnel`

### 2.5 复核发现的缺陷：隧道幂等守卫**形同虚设**（已修复）

复核 `_ops\run_tunnel.ps1` 时发现守卫写错了判据：

```powershell
# 错（原版）：拿 tunnel id 去匹配命令行
$tid = 'e9c34312-ea83-4674-84c4-15b08298e4e9'
... Where-Object { $_.CommandLine -like ('*' + $tid + '*') }
if ($running) { exit 0 }
```

**根因**：Cloudflare 的 tunnel token 是一个**整体 base64 字符串**，tunnel id 被编码在**里面**：

```
token(184 B) = base64( {"a":"<account>","t":"e9c34312-ea83-4674-84c4-15b08298e4e9","s":"<secret>"} )
```

⇒ token 原文里**根本不含** `e9c34312` 这串字面量（实测 `'e9c34312' in token == False`）。
所以守卫**永远不成立**，每次触发都会**再拉起一个重复的 cloudflared 进程**。
（同理：对进程命令行/脚本 grep tunnel id 一律是**假阴性**，必须 base64 解码后再比。）

**修复**：改为拿 **token 本身**匹配命令行（token 原样出现在 `--token` 之后）：

```powershell
$cmds   = @(Get-CimInstance Win32_Process -Filter "Name='cloudflared.exe'" -ErrorAction SilentlyContinue |
            Select-Object -ExpandProperty CommandLine)
$joined = ($cmds -join "`n")
if ($joined.Contains($tok)) { exit 0 }
```

**连带修掉的第二个坑**：守卫的提示行不能写进 `tunnel.log` ——
隧道运行时 `*>>` 重定向**占着该文件句柄**，`Add-Content` 会抛
`文件…正由另一进程使用，因此该进程无法访问此文件`。改为写独立的 `logs\tunnel_guard.log`。

**验证**（触发两次）：

| 检查 | 结果 |
|---|---|
| cloudflared 进程数 before → after → final | **3 → 3 → 3**（未产生重复） |
| `tunnel_guard.log` | 两次均记录 `web tunnel already running, skip` |
| 语法检查 `[Parser]::ParseFile` | **0 error** |
| 公网 `geoflow` / `api/health` | 均 **200**（未受影响） |

改动留档：`_ops\run_tunnel.ps1`（1379 B），备份 `run_tunnel.ps1.bak.20260918-191422` / `-191516`。

### 2.6 ⚠️ 待决风险：SSH 隧道（`b13d…`）**没有开机自启**

|---|---|---|---|

| 18120 | 2026-09-17 02:29 | `qiujianxiu`（Console 会话 1） | **`b13d485e-…`** ← **SSH/SMB/FileBrowser 走这条** |
| 8804 | 2026-09-18 18:50 | `qiujianxiu`（Console 会话 1） | `e9c34312-…`（网站，已纳入计划任务） |

⇒ **一旦重启（或会话 1 注销），`b13d` 不会自动恢复，SSH 入口即失效**；
而公钥认证被拒、只能密码登录 ⇒ 届时需**有人到机器跟前**手动拉起隧道才能重新接入。**这是当前最大的可用性风险。**

补救方案（**未执行，等你确认**）：照 `CGDA-Tunnel` 的写法，为 `b13d` 也建一个
`CGDA-SshTunnel` 计划任务（ONLOGON + 以 **token** 为判据的幂等守卫），
token 从 PID 18120 的命令行提取后写入 `_ops\run_ssh_tunnel.ps1`。**不动现有进程**，纯增量。

> 另：本轮排查时，`Format-List` 会把超长命令行**折行**，导致脱敏正则只吃到第一行、
> 折行后的**残余 token 片段被打印出来**。web 与 ssh 两条 token 都有**部分片段**出现在会话记录里
> ⇒ 建议本轮收尾后**轮换这两个 tunnel token**（Cloudflare Zero Trust → Networks → Tunnels → 刷新 token）。

### 2.7 「登录不进去」的排查结论（2026-09-18 晚，两个**互相独立**的原因）

用户反馈远端系统已启动但 admin 登录不进去。排查后确认是**两件事叠加**，不是同一个问题。

#### 原因 A（主因）：用的是旧口令 `cgda-dev-admin`

远端用户库 `E:\Project\CGDA\Data\_runtime\workflow_state\users.sqlite3` 是**新建数据根后重新播种**的：

| 事实 | 值 |
|---|---|
| 用户数 | **1**（仅 `admin`，role=admin，enabled=1） |
| 创建时间 | 2026-09-18T10:46:38Z（= 18:46 本地，P5 启动时播种） |
| 播种来源 | 远端 `Code/backend/.env` 的 `BACKEND_ADMIN_PASSWORD` |
| `session count` | **0** ⇒ 建库至今**从未成功登录过一次** |

**关键语义**（`.env` 里也有注释）：`BACKEND_ADMIN_PASSWORD` **只在用户表为空时用于初始播种**；
库中已有账号后改它**完全无效**。而 `.env` 里的实际值是 **2026-09-16 轮换后的强口令**
（见 `.env` 的「运行期账号口令台账」`CGDA_ACCOUNT_admin_PASSWORD`），**不是** `cgda-dev-admin`。
且 `cgda-dev-admin` 已被列入 `app/services/passwords.py::WEAK_DENYLIST` —— 当时判定**永远无法再被设上**
（⚠️ 该判定已在同一晚被 §2.8 的**开发期双门控旁路**推翻，请看 §2.8 再下结论）。

⚠️ **远端只有 `admin` 一个账号**：`admin01` / `admin02` / `onlyread` 在本地库里有，**远端没有**
（远端库是新建的，不是从本地拷的）。所以拿这几个账号登录也会失败。

**离线校验（零风险，推荐做法）**：不要反复 POST `/auth/login` 试口令 —— 会累加**账号级失败计数**。
直接比对库里的 PBKDF2 哈希即可定性：

```python
# pbkdf2-sha256, 200k iters, 格式 "pbkdf2-sha256$<iters>$<salt_hex>$<digest_hex>"
d = hashlib.pbkdf2_hmac("sha256", candidate.encode(), bytes.fromhex(salt_hex), int(iters)).hex()
print(d == digest_hex)
```

实测（2026-09-18 20:05，**§2.8 之前**）：`CGDA_ACCOUNT_admin_PASSWORD` 的值 **MATCH**，
`cgda-dev-admin` **不匹配**。同法核对 `password_hash` 对得上台账 ⇒ 台账与库一致。

> ⚠️ 上条只是**当时的排查快照**。§2.8 已按主人决策把开发期口令统一改成 `cgda-dev-admin`，
> 所以**现在**再核对会得到相反结果。判断当前口令请以 §2.8 为准，不要用本段复核。

### 2.8 开发期统一口令 `cgda-dev-admin`（2026-09-18 晚，主人决策；已实施）

**决策**：开发阶段所有账号口令统一为 `cgda-dev-admin`，方便反复登录多账号调试；
**正式交付前**再改回随机初始口令。

**障碍**：`cgda-dev-admin` 同时违反 `app/services/passwords.py::validate_password` 的两条规则 ——
① 命中 `WEAK_DENYLIST`；② 含用户名字段（`admin`）。直接调用会被拒绝 —— 这正是 §2.7 里
「永远无法再被设上」结论的来源。

**处置：加一个双门控旁路**（两个条件**必须同时**满足）：

| 门 | 变量 | 取值 |
|---|---|---|
| 开关 | `BACKEND_PASSWORD_POLICY_ALLOW_WEAK` | `1` / `true` / `yes` / `on` |
| 环境 | `BACKEND_ENV` | `development` / `dev` / `test` / `testing` |

```python
WEAK_POLICY_BYPASS_ENV_VAR = "BACKEND_PASSWORD_POLICY_ALLOW_WEAK"
_WEAK_BYPASS_ENVS = frozenset({"development", "dev", "test", "testing"})

def _weak_policy_bypass() -> bool:
    flag = os.getenv(WEAK_POLICY_BYPASS_ENV_VAR, "").strip().lower()
    if flag not in {"1", "true", "yes", "on"}:
        return False
    env = os.getenv("BACKEND_ENV", "").strip().lower()
    return env in _WEAK_BYPASS_ENVS
```

`validate_password` 命中旁路时直接返回，并打一条带用户名的 `WARNING`，便于日后审计。

**为什么要「双」门控**：`BACKEND_ENV=production` 时，即使运维误设了开关也**不可能**放宽 ——
生产环境的口令强度底线不依赖人的记性，而是一条代码级硬约束。

**落地清单**：

| 项 | 内容 |
|---|---|
| `.env` | 追加 `BACKEND_PASSWORD_POLICY_ALLOW_WEAK=true`；**该文件 gitignore，两机各自维护、不提交** |
| 台账 | `CGDA_ACCOUNT_*_PASSWORD` 就地覆盖为 `cgda-dev-admin`，并插「开发期覆盖」注释标明什么时候撤（台账是**运行期真源**；`BACKEND_ADMIN_PASSWORD` 只在用户表为空时播种，之后完全惰性） |
| 账号 | 远端 `admin`；本地 `admin` / `admin01` / `admin02` / `onlyread` —— 全部改为 `cgda-dev-admin`，登录实测 200 |
| 测试 | 新增 6 条（默认关闭 / flag 值必须为真 / 必须同时是开发环境 / 强口令不受影响…），`Test/backend/test_passwords.py` 共 **16 条全绿** |
| 提交 | `cca71f5a feat(auth): 增加开发期口令强度策略旁路开关` |

**撤回步骤（对外交付前必做）**：

1. 删掉 `.env` 里 `BACKEND_PASSWORD_POLICY_ALLOW_WEAK=true` 与台账的「开发期覆盖」注释；
2. 用 `scripts/rotate_user_passwords.py` 逐账号换成随机初始口令（`set --user X --password <随机>`）；
3. `launch.py restart backend` 使其生效；
4. 顺手清掉试错产生的锁定：`redis-cli -p 16379 del cgda:loginfail:*`
   （注意 Redis 容器映射到宿主 **16379**，不是 6379）。

⚠️ **本次顺带踩到的坑：`.env` 混合行尾**。本机 `.env` 以 **LF** 为主，但 `Add-Content` 追加写入的是 **CRLF**
⇒ 文件变成混合行尾。随后按锚点插注释的脚本判断失误 —— **`"\r\n" in text` 在「以 LF 为主、夹几行 CRLF」的文件上为真**，
于是它按 CRLF 切分 → 锚点找不到 → 注释被丢到文件末尾。
修法：先按**占多数**的行尾统一，再插注（`_ops\fix_env_note.py`）。
**教训：改 `.env` 前先确认行尾一致性；不要用 `"\r\n" in text` 判断「这是不是 CRLF 文件」。**

### 2.9 应用栈**没有自愈能力** —— 启动守卫修复 + 新增 `CGDA-Stack-Watchdog`（已实施）

#### 缺陷 1：`launch.py` 的监控循环只**报告**，从不重启

`launch.py start`（全量档）末尾：

```python
while not pm._shutting_down:
    time.sleep(5)
    pm.monitor()
```

而 `ProcessManager.monitor()` 的 docstring 就是「监控所有进程，有进程异常退出时**报告**」——
它只打 `xxx 异常退出` 日志、并**接管外部已重启**的进程，**自己从不重启任何东西**。

叠加 `CGDA-Stack` 只有 `LogonTrigger`（登录才跑一次）+ `MultipleInstancesPolicy=IgnoreNew`，
结论：**登录之后后端进程若中途挂掉，没有任何机制会把它拉起来**，只能等人工或下次登录。

这与 §2.6/§2.7 的隧道问题是同一类 —— 隧道早就有 5 分钟看门狗，**应用栈却没有**。

#### 缺陷 2：启动守卫只看 5175 ⇒ 永远早退

原 `_ops\start_stack.ps1` 的守卫：

```powershell
if (Get-NetTCPConnection -LocalPort 5175 -State Listen -ErrorAction SilentlyContinue) { exit 0 }
```

5175 是 **`cgda-gateway-nginx` 容器**（`restart: unless-stopped`）占用的 ——
**后端全死它也照样 LISTENING**。于是守卫恒为真、恒早退，`launch.py start` **从来没被触发过**
（后端缺失时也不会被拉起，例如「注销后再登录」这种容器还在、后端没了的情形）。

修复：**两个端口都要在**。

```powershell
$gwUp = Get-NetTCPConnection -LocalPort 5175 -State Listen -ErrorAction SilentlyContinue
$beUp = Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue
if ($gwUp -and $beUp) { Add-Content $glog 'stack healthy (5175+8000), skip'; exit 0 }
```

守卫日志**必须另开文件**（`stack_guard.log`）：`launch.py start` 一旦跑起来就用 `*>>` 独占
`p5_stack.log`，此时 `Add-Content` 会报「文件正被另一进程使用」。（与 §2.5 隧道守卫同一个坑。）

#### 新增：`CGDA-Stack-Watchdog`（每 5 分钟）

`_ops\stack_watchdog.py` + `stack_watchdog.cmd`：

| 项 | 值 |
|---|---|
| 触发 | `Interval = PT5M`，**无 Duration ⇒ 无限重复**；`IgnoreNew` 防重叠 |
| 主体 | `qiujianxiu`，`LogonType=InteractiveToken` |
| 判定 | 网关(5175)**端口**在 ∧ 后端(8000) 端口在且 `/health`=200 ∧ 台账里 `fastapi`/`beat`/`worker-*` **全部存活** |
| 修复 | 网关死 → `launch.py start docker`；后端死或有用例 pid 消失 → `launch.py restart backend` |
| 去重 | 冷却 600s，状态存 `logs\stack_watchdog.state.json` |
| 心跳 | 健康且状态未变时**静默**；每小时写一行 `HEARTBEAT`（否则任务本身坏掉也无人知） |

三个设计要点（都是踩过才写的）：

1. **网关活性必须用端口探，不能用 HTTP**：:5175 反代到后端，后端一死后 `/health` 立刻 502 ——
   用 HTTP 根本分不清「网关死」还是「后端死」。
2. **用 `restart backend` 而不是 `start backend`**：`restart` 会先 `_stop_backend_app_processes()`
   清扫旧进程，不会叠世代；`start` 没有清扫逻辑。
3. **必须用 pid 台账判活**才能覆盖 worker / beat 单独挂掉 —— 端口探完全看不到这种故障。

**实测覆盖**（两个分支都验过）：

- 自测 `_ops\watchdog_selftest.py`：真台账 → `healthy`，不动；注入 `beat:999999` / `worker-ghost:999998`
  （并用非后端键 `frontend:1` 作对照）→ 精确报出两个死 pid、**正确过滤掉** `frontend`，计划动作只有 `restart backend`；
  dry-run **不写状态文件**（无污染）。
- 任务链路：`schtasks /Run /TN CGDA-Stack-Watchdog` 后日志写入 `HEARTBEAT healthy | ...` ⇒ 计划任务 → cmd → python 全通。
- 守卫修复：`schtasks /Run /TN CGDA-Stack` 后 `stack_guard.log` 写入 `stack healthy (5175+8000), skip`，
  且 **`launcher_pids.json` 与 `p5_stack.log` 的 mtime 均未变** ⇒ 确认没有真的再启一套。

备份与移除：脚本备份 `start_stack.ps1.bak.20260918-202948`；
移除看门狗 `schtasks /Delete /TN CGDA-Stack-Watchdog /F`。

⚠️ 与隧道看门狗相同：schtasks 默认 `DisallowStartIfOnBatteries=true`，**台式机无影响**，迁笔记本时需改。

#### 顺带澄清：3 个 `cloudflared` 进程**不是**重复

排查时看到 3 个 `cloudflared` 进程，一度怀疑 §2.5 的守卫又失效了。**解码 token 后确认是三条不同用途**：

| PID | 创建时间 | tunnel id | 用途 |
|---|---|---|---|
| 5596 | 2026-09-16T22:32 | （无 `--token` 参数） | `Cloudflared` **Windows 服务**（LocalSystem/Auto，父进程 `services.exe`）承载 |
| 18120 | 2026-09-17T02:29 | `b13d485e-…` | **SSH 隧道**（用户态手动进程，即 §2.6 那条） |
| 20936 | 2026-09-18T20:04 | `e9c34312-…` | **网站隧道**（§2.7 原因 B 恢复时拉起的那条） |

⚠️ **教训**：先前按 base64 **前缀**判断「两条 token 一样」是错的 —— 两条 token 的
`{"a":…,"t":…}` 前缀相同（同账号、同字段序），差异在 `t` 值处被截断掩盖了。
**base64 截断前缀不能当作「相同」的证据，必须解码后比 `t` 字段。**（工具：`_ops\probe_tunnel.py`。）

> 🔵 待确认：`Cloudflared` 服务（PID 5596）的 `PathName` **无参数**，且
> `systemprofile\.cloudflared\config.yml` 不存在 ⇒ 从 SSH 侧无法判断它承载哪条隧道，
> 需在远端桌面用 `cloudflared tunnel info` / 服务日志确认它是否在空转。
> 它**不是** `b13d`（`b13d` 由 PID 18120 用户态进程承载），所以 **§2.6 的结论不变**。

## 4. 再开发闭环

```
远端编辑代码 (codegraph)  →  git commit  →  git push origin dev  →  本地 git pull 校验
```

```bash
# 远端只推 dev
git checkout dev && git add <路径> && git commit -m "type: ..."
git push origin dev

# 阶段性发布：main 手动合并（不冲突；要留合并点就加 --no-ff）
git checkout main && git pull --ff-only origin main
git merge dev --no-edit && git push origin main && git checkout dev
```

- **严禁 `git add -A` / `git commit -a`**（会把未复制子树记成删除）。
- 提交信息用 Conventional Commits（pre-commit 强制）。
