```

docker tag  docker.m.daocloud.io/library/redis:7.4.10-alpine redis:7.4.10-alpine

```

**并已为将来铺路**：`C:\Users\qiujianxiu\.docker\daemon.json` 已加入 `registry-mirrors`
（备份 `daemon.json.bak.p4`）——**下次 Docker Desktop 重启后自动生效**，届时无需再手工 retag。

### 2.2 非交互 SSH 会话下 Docker 凭据助手必失败

报错：
```
error getting credentials - err: exit status 1, out: `A specified logon session does not exist.`
```
原因：SSH 是**网络登录**会话，无交互登录会话 ⇒ `docker-credential-desktop` 访问 Windows 凭据管理器失败。
且 Docker Desktop 的 CLI 在 config **未指定 `credsStore` 时会默认用 `desktop`**（所以 `--config` 指向干净配置也照样报错）。

**处置**：仓库外建匿名凭据助手 + 专用 `DOCKER_CONFIG`（两者必须同时生效）：

| 文件 | 作用 |
|---|---|
| `E:\Project\CGDA\_ops\docker-cred\docker-credential-cgdaanon.cmd` | `get` 回 `{"Username":"","Secret":""}` ⇒ 视为无凭据 → 匿名拉取 |
| `E:\Project\CGDA\_ops\docker-config\config.json` | `{"auths":{},"credsStore":"cgdaanon"}` |

> **踩坑**：助手 `get` 若**什么都不输出**（exit 0），docker 会报 `EOF`；必须回**合法 JSON**。

### 2.3 服务进程不能靠 SSH 会话存活 ⇒ 用计划任务

`launch.py` 用 `CREATE_NO_WINDOW` 拉起子进程，**SSH 会话一断就被回收**（实测：detached 的 `Start-Process`/`cmd` 全部秒退）。
**处置**：用 Windows 计划任务把启动动作"脱离会话"：

| 计划任务 | 触发 | 幂等守卫 |
|---|---|---|
| `CGDA-Stack` | ONLOGON | 若 `:5175` 已在监听则直接退出 |
| `CGDA-Tunnel` | ONLOGON | 若已有**含同一 token** 的 `cloudflared.exe` 则直接退出 |

手工拉起：`schtasks /Run /TN CGDA-Stack` / `schtasks /Run /TN CGDA-Tunnel`

### 2.4 公网入口用的是**另一个**隧道

远端常驻的 `Cloudflared` 服务跑的是 tunnel **`b13d…`**；而 `cgdas.dpdns.org` 的 ingress 在 tunnel
**`e9c34312-ea83-4674-84c4-15b08298e4e9`** 上——它原本**没在运行**，所以 `geoflow`/`api` 都是 Cloudflare **1033**。
**处置**：以独立进程额外拉起该隧道（不动原有服务）。其 dashboard ingress 已确认存在：

```
geoflow.cgdas.dpdns.org  ->  http://localhost:5175
api.cgdas.dpdns.org      ->  http://localhost:8000
（无匹配 -> http_status:404）
```

### 2.5 复核发现的缺陷：隧道幂等守卫**形同虚设**（已修复）

复核 `_ops\run_tunnel.ps1` 时发现守卫写错了判据：

```powershell
# 错（原版）：拿 tunnel id 去匹配命令行
$tid = 'e9c34312-ea83-4674-84c4-15b08298e4e9'
... Where-Object { $_.CommandLine -like ('*' + $tid + '*') }
if ($running) { exit 0 }
```

**根因**：Cloudflare 的 tunnel token 是一个**整体 base64 字符串**，tunnel id 被编码在**里面**：

```
token(184 B) = base64( {"a":"<account>","t":"e9c34312-ea83-4674-84c4-15b08298e4e9","s":"<secret>"} )
```

⇒ token 原文里**根本不含** `e9c34312` 这串字面量（实测 `'e9c34312' in token == False`）。
所以守卫**永远不成立**，每次触发都会**再拉起一个重复的 cloudflared 进程**。
（同理：对进程命令行/脚本 grep tunnel id 一律是**假阴性**，必须 base64 解码后再比。）

**修复**：改为拿 **token 本身**匹配命令行（token 原样出现在 `--token` 之后）：

```powershell
$cmds   = @(Get-CimInstance Win32_Process -Filter "Name='cloudflared.exe'" -ErrorAction SilentlyContinue |
            Select-Object -ExpandProperty CommandLine)
$joined = ($cmds -join "`n")
if ($joined.Contains($tok)) { exit 0 }
```

**连带修掉的第二个坑**：守卫的提示行不能写进 `tunnel.log` ——
隧道运行时 `*>>` 重定向**占着该文件句柄**，`Add-Content` 会抛
`文件…正由另一进程使用，因此该进程无法访问此文件`。改为写独立的 `logs\tunnel_guard.log`。

**验证**（触发两次）：

| 检查 | 结果 |
|---|---|
| cloudflared 进程数 before → after → final | **3 → 3 → 3**（未产生重复） |
| `tunnel_guard.log` | 两次均记录 `web tunnel already running, skip` |
| 语法检查 `[Parser]::ParseFile` | **0 error** |
| 公网 `geoflow` / `api/health` | 均 **200**（未受影响） |

改动留档：`_ops\run_tunnel.ps1`（1379 B），备份 `run_tunnel.ps1.bak.20260918-191422` / `-191516`。

### 2.6 ⚠️ 待决风险：SSH 隧道（`b13d…`）**没有开机自启**

复核三个 cloudflared 进程后确认：

| PID | 启动时间 | 运行身份 | 隧道 |
|---|---|---|---|
| 5596 | 2026-09-16 22:32 | `NT AUTHORITY\SYSTEM`（`Cloudflared` 服务，AUTO_START） | **无参数、无 token** |
| 18120 | 2026-09-17 02:29 | `qiujianxiu`（Console 会话 1） | **`b13d485e-…`** ← **SSH/SMB/FileBrowser 走这条** |
| 8804 | 2026-09-18 18:50 | `qiujianxiu`（Console 会话 1） | `e9c34312-…`（网站，已纳入计划任务） |

关键事实：
- `Cloudflared` 服务的 token 存储目录**都不存在**（`systemprofile\.cloudflared` = False、
  `C:\ProgramData\Cloudflared` = False），且 `ImagePath` **不带任何参数** ⇒ **该服务不持有 `b13d` 隧道**。
- `b13d` 只存在于 PID 18120 的命令行里，**没有任何计划任务/服务**托管它（非 Microsoft 计划任务里查无此项）。

⇒ **一旦重启（或会话 1 注销），`b13d` 不会自动恢复，SSH 入口即失效**；
而公钥认证被拒、只能密码登录 ⇒ 届时需**有人到机器跟前**手动拉起隧道才能重新接入。**这是当前最大的可用性风险。**

补救方案（**未执行，等你确认**）：照 `CGDA-Tunnel` 的写法，为 `b13d` 也建一个
`CGDA-SshTunnel` 计划任务（ONLOGON + 以 **token** 为判据的幂等守卫），
token 从 PID 18120 的命令行提取后写入 `_ops\run_ssh_tunnel.ps1`。**不动现有进程**，纯增量。

> 另：本轮排查时，`Format-List` 会把超长命令行**折行**，导致脱敏正则只吃到第一行、
> 折行后的**残余 token 片段被打印出来**。web 与 ssh 两条 token 都有**部分片段**出现在会话记录里
> ⇒ 建议本轮收尾后**轮换这两个 tunnel token**（Cloudflare Zero Trust → Networks → Tunnels → 刷新 token）。

### 2.7 「登录不进去」的排查结论（2026-09-18 晚，两个**互相独立**的原因）

用户反馈远端系统已启动但 admin 登录不进去。排查后确认是**两件事叠加**，不是同一个问题。

#### 原因 A（主因）：用的是旧口令 `cgda-dev-admin`

远端用户库 `E:\Project\CGDA\Data\_runtime\workflow_state\users.sqlite3` 是**新建数据根后重新播种**的：

| 事实 | 值 |
|---|---|
| 用户数 | **1**（仅 `admin`，role=admin，enabled=1） |
| 创建时间 | 2026-09-18T10:46:38Z（= 18:46 本地，P5 启动时播种） |
| 播种来源 | 远端 `Code/backend/.env` 的 `BACKEND_ADMIN_PASSWORD` |
| `session count` | **0** ⇒ 建库至今**从未成功登录过一次** |

**关键语义**（`.env` 里也有注释）：`BACKEND_ADMIN_PASSWORD` **只在用户表为空时用于初始播种**；
库中已有账号后改它**完全无效**。而 `.env` 里的实际值是 **2026-09-16 轮换后的强口令**
（见 `.env` 的「运行期账号口令台账」`CGDA_ACCOUNT_admin_PASSWORD`），**不是** `cgda-dev-admin`。
且 `cgda-dev-admin` 已被列入 `app/services/passwords.py::WEAK_DENYLIST` —— **永远无法再被设上**。

⚠️ **远端只有 `admin` 一个账号**：`admin01` / `admin02` / `onlyread` 在本地库里有，**远端没有**
（远端库是新建的，不是从本地拷的）。所以拿这几个账号登录也会失败。

**离线校验（零风险，推荐做法）**：不要反复 POST `/auth/login` 试口令 —— 会累加**账号级失败计数**。
直接比对库里的 PBKDF2 哈希即可定性：

```python
# pbkdf2-sha256, 200k iters, 格式 "pbkdf2-sha256$<iters>$<salt_hex>$<digest_hex>"
d = hashlib.pbkdf2_hmac("sha256", candidate.encode(), bytes.fromhex(salt_hex), int(iters)).hex()
print(d == digest_hex)
```

实测：`CGDA_ACCOUNT_admin_PASSWORD` 的值 **MATCH**，`cgda-dev-admin` **不匹配**。
同法核对 `password_hash` 对得上台账 ⇒ 台账与库一致。

#### 原因 B：网站隧道进程已死，公网整体 1033

排查过程中发现 `https://api.cgdas.dpdns.org/auth/login` 返回 **530 + `error code: 1033`**，
即隧道已断（栈本身正常：`localhost:5175` → 200、`localhost:8000/health` → ok）：

```
tunnel.log:
2026-09-18T11:54:44Z ERR Connection terminated connIndex=2/3
2026-09-18T11:54:44Z ERR no more connections active and exiting
2026-09-18T11:54:44Z INF Tunnel server stopped
```

`CGDA-Tunnel` 只挂了 **ONLOGON** 触发 ⇒ **进程一死就没有任何机制拉起它**，
公网会一直 1033 直到下次登录/手工干预。**已于 20:04:42 恢复**（新进程 PID 20936），
公网与登录随即恢复 200。

#### 处置：新增 5 分钟看门狗（`CGDA-Tunnel-Watchdog`）

因为 §2.5 已把守卫修成**真正幂等**，重复执行是安全的，所以加一条定时任务兜底：

```
schtasks /Create /TN "CGDA-Tunnel-Watchdog" /SC MINUTE /MO 5 ^
         /TR "E:\Project\CGDA\_ops\run_tunnel.cmd" /F
```

| 项 | 值 |
|---|---|
| 触发 | `Interval = PT5M`，**无 Duration ⇒ 无限重复** |
| 主体 | `qiujianxiu`，`LogonType=InteractiveToken`（需该用户处于登录态） |
| 行为 | 隧活在 → 守卫 `exit 0`（仅写一行 skip 日志）；隧死 → 拉起 |

验证：手动触发两次，`cloudflared` 进程数恒为 3，`tunnel_guard.log` 依次记录
`starting web tunnel` → `web tunnel already running, skip`（**两个分支都实测覆盖**）。

⚠️ 该任务的 `DisallowStartIfOnBatteries=true` / `StopIfGoingOnBatteries=true` 是 schtasks 默认值。
**本机是台式机（无电池）不影响**；若日后迁到笔记本，需改这两项，否则拔电时看门狗不跑。

移除方式：`schtasks /Delete /TN "CGDA-Tunnel-Watchdog" /F`

## 4. 再开发闭环

```
远端编辑代码 (codegraph)  →  git commit  →  git push origin dev  →  本地 git pull 校验
```

```bash
# 远端只推 dev
git checkout dev && git add <路径> && git commit -m "type: ..."
git push origin dev

# 阶段性发布：main 手动合并（不冲突；要留合并点就加 --no-ff）
git checkout main && git pull --ff-only origin main
git merge dev --no-edit && git push origin main && git checkout dev
```

- **严禁 `git add -A` / `git commit -a`**（会把未复制子树记成删除）。
- 提交信息用 Conventional Commits（pre-commit 强制）。
