# CGDA 项目工程级优化路线图

> 性质：工程级分析报告（不改代码）。覆盖后端目录/缓存/依赖 + 前端结构/依赖。每项标注根因 / 严重度 / 解决方案 / 风险等级 / 验证方式，供逐项决策执行。
> 范围决策：优先领域=工程级分析报告；风险偏好=先分析后定夺（每项标风险等级）；前端=纳入。

---

## 1. 摘要

CGDA 已进入工程落地阶段：`workflow-runs` 主链、天气瓦片渲染、Celery/Redis/MinIO 基础设施均可运行，前后端契约机制（`gen:types` + `check:openapi`）已建立，整体架构选型合理（FastAPI + Celery 分层、MapLibre 2D 主路径、服务/路由按域划分雏形已现）。但"快速迭代中累积的工程债"已形成三个结构性风险域：

1. **缓存与数据目录失控**：12 种缓存机制各自为政，artifacts 无生命周期且持续增长（2110 文件），三级缓存一致性靠人工协调，存在"数据复活"与孤儿文件累积。
2. **后端分层未贯彻**：`app/services/` 50 个扁平文件分组不彻底，存在 service→task 反向依赖，路由分散三处且命名不统一，编排逻辑渗入 task 层。
3. **前端巨型化与依赖污染**：多个 God Store / 巨型 SFC（最大 2949 行），天气状态分散 6+ 处，未使用的 cesium 重依赖（40MB+）误入 dependencies，依赖根因被 `.npmrc` 掩盖。

**核心问题浓缩（按影响排序）**：
- P0：artifacts 孤儿持续增长无回收；天气三级缓存"复活"；service→task 反向依赖；cesium/vue-cesium 死重依赖。
- P1：缓存机制碎片化无统一治理；services/ 分组不彻底；路由三处分裂；God Store / 巨型 SFC；契约校验只验路径不验 schema；sys.path 动态 importlib 脆弱边界。
- P2：遗留别名/残留文件；跨包命名碰撞；测试污染目录；死代码清理。

## 3. 后端缓存与数据目录优化

### B1. 缓存机制碎片化，无统一治理
- **根因**：12 套缓存按需逐个引入，无统一抽象层、无统一失效入口、无命中率监控。
- **严重度**：高
- **解决方案**（多级缓存分层治理最佳实践）：
  - 引入统一 `CacheManager` 抽象，按"域 + 层级"注册：每个缓存声明 `domain`(weather/config/workflow/gee)、`tier`(L0 内存/L1 Redis/L2 文件)、`ttl`、`invalidation_strategy`。
  - 统一失效入口：所有失效走 `CacheManager.invalidate(domain, key|tag)`，内部按注册表级联清理 L0/L1/L2，禁止业务代码直接调 Redis DEL 或删文件。
  - 采用**失效优先（删除而非更新）**策略，避免并发写脏数据回填。
  - L0 内存 TTL 显著短于 L1 Redis（差异化 TTL 兜底，如 L0 5min / L1 30min），主动失效失败也能最终一致。
  - 暴露 `/health/cache` 诊断端点聚合所有缓存命中率/容量/断路器状态。
- **风险等级**：中（统一抽象需改动多处调用点，可渐进式适配，先注册后迁移）
- **验证**：`tests/test_cache_manager.py` 覆盖级联失效；`/health/cache` 返回所有域状态。

### B2. artifacts 无生命周期，孤儿文件持续增长
- **根因**：2110 文件无 TTL、无清理任务、无 API；workflow_runs 30 天清理后只删 DB 记录不删文件，产生孤儿 artifact。
- **严重度**：高
- **解决方案**（引用计数 GC + 延迟清理 + mark-sweep）：
  - 三层回收模型：(1) 引用计数——artifact 表增加 `ref_count`，run 引用 +1，run 清理 -1，归零标记 `orphaned_at`；(2) 延迟删除——`orphaned_at` 后保留宽限期（如 7 天）再批量删，支持误删恢复；(3) mark-sweep 兜底——周期任务扫描文件系统所有 artifact 与 DB 引用表 diff，未引用且 mtime 早于基线的标记孤儿删除。
  - MinIO 生命周期策略：对 artifacts bucket 按前缀配 TTL 规则作存储层兜底。
  - 事务一致性：workflow_run 清理任务中，DB 记录删除与 artifact `ref_count` 递减放同一事务边界。
  - 新增 `DELETE /artifacts/{id}` API 与 `GET /artifacts/orphans` 诊断端点。
- **涉及文件**：`app/services/result_storage.py`、`app/services/object_store.py`、`app/api/routers/artifact_router.py`、`app/tasks/cleanup_tasks.py`、`app/services/workflow_repository.py`。
- **风险等级**：中（mark-sweep 需保守宽限期防误删；引用计数需处理并发递减）
- **验证**：`tests/test_artifact_lifecycle.py`（引用计数递减、孤儿标记、宽限期回收）；构造 run 清理后验证文件被标记而非立即删除。

### B3. cleanup_cache_files Beat 任务不覆盖 weatherengine 文件缓存子目录
- **根因**：清理任务遍历目录路径未含 `.data/cache/weatherengine/`，天气文件 L2 只增不减。
- **严重度**：中
- **解决方案**：长期按 B1 `CacheManager` 注册表驱动清理；过渡期显式补全 weatherengine 子目录到清理 glob 并加目录存在性校验。
- **涉及文件**：`app/tasks/cleanup_tasks.py`。
- **风险等级**：低
- **验证**：`tests/test_cleanup_cache_files.py`；`python launch.py start beat` 后观察 `.data/cache/weatherengine/` 体积不再单调增长。

### B4. 天气三级缓存一致性风险（"复活"问题）
- **根因**：改 `WeatherLayerSpec` 字段后需同时清 Redis（`weather:point/grid:*`）+ 文件 L2 + 重启进程清 L0 LRU；文件缓存会 backfill 旧数据导致"复活"。
- **严重度**：高
- **解决方案**（失效优先 + 差异化 TTL + SWR）：
  - 失效优先 + 级联删除：spec 变更时由 `CacheManager.invalidate("weather", tag=spec_id)` 级联删 L1+L2+L0，删除而非更新，杜绝 backfill 复活。
  - **写入时带 spec 版本号（治本）**：缓存 key/文件名嵌入 `spec_version`（spec 哈希），旧版本缓存自然失效不可复活——旧 key 即使残留也查不到。
  - 差异化 TTL 兜底：L0 LRU 加 TTL（5min，当前无）；L1 Redis 3600s；L2 文件短于 L1。
  - 多进程 L0 失效：spec 变更后通过 Redis Pub/Sub 广播失效事件，各 FastAPI/Celery 进程订阅后清本地 L0 LRU，避免必须重启。
  - 可选 SWR + singleflight：点查先返回旧值后台刷新，配锁防击穿。
- **涉及文件**：`app/weatherengine/client.py`、`app/weatherengine/tile_service.py`、`app/services/cache_service.py`（CacheManager）。
- **风险等级**：高（spec_version 嵌入 key 需改缓存键构造与读取逻辑，影响天气热路径，需充分测试）
- **验证**：`pytest tests/test_weather_point_service.py tests/test_weatherengine_service.py -q`；构造 spec 字段变更场景验证三级缓存均失效且无 backfill 复活；`python launch.py start fastapi` 后请求 `/weather/tiles/{layer_id}/{z}/{x}/{y}`。

### B5. 两套 CircuitBreaker（内嵌式不被诊断端点监控）
- **根因**：`services/circuit_breaker.py`（集中式，被 `/health` 监控）与 `weatherengine/client.py`（内嵌式，盲区）并存。
- **严重度**：中
- **解决方案**：统一为集中式 `CircuitBreaker`，weatherengine client 注入而非自建；迁移后断路器状态自动纳入 `/health` 与 B1 `/health/cache` 聚合。
- **涉及文件**：`app/weatherengine/client.py`、`app/services/circuit_breaker.py`。
- **风险等级**：低
- **验证**：`pytest tests/test_fetch_gateway.py -q`；`/health` 返回 weatherengine 断路器状态。

### B6. 天气瓦片 LRU 内存缓存无 TTL，重启丢失
- **根因**：256 条 LRU 无过期，进程重启全丢，冷启动雪崩。
- **严重度**：中
- **解决方案**：LRU 加 `expireAfterWrite` TTL（5min，与 B4 差异化 TTL 一致）；冷启动可选从 L1 Redis 预热 L0；纳入 B1 `CacheManager` 注册表参与级联失效与 Pub/Sub 广播。
- **涉及文件**：`app/weatherengine/tile_service.py`。
- **风险等级**：低
- **验证**：`pytest tests/test_weather_tile_service.py -q`；重启 fastapi 后首次请求验证命中 Redis 而非全 miss。

### B7. Redis FLUSHDB 副作用（清预算计数器/去重锁）
- **根因**：`launch.py flush` 执行 `FLUSHDB` 清空整个 Redis DB，连带清预算计数器（致超限）与去重锁（致重复请求），但不影响进程内断路器/LRU。
- **严重度**：中
- **解决方案**：flush 改为按 key 前缀选择性删除（`weather:*` 等缓存前缀），保留 `budget:*`、`dedup:*`、限流计数器；或将缓存与预算/去重隔离到不同 Redis DB（cache=db0，control=db1），flush 只清 db0；flush 后自动重建预算计数器或加启动校验告警。
- **涉及文件**：`launch.py`、`app/core/redis_client.py`、`app/core/config.py`。
- **风险等级**：中（前缀删除需精确列举所有缓存前缀；分库需改连接配置）
- **验证**：`python launch.py flush` 后验证 `budget:*` 计数器仍在；构造重复请求验证去重锁未失效。

### B8. DataCacheService（materialized）无自动清理
- **根因**：materialized 缓存无 TTL、无清理任务。
- **严重度**：中
- **解决方案**：纳入 B1 `CacheManager` 注册表，声明 TTL 与失效策略；复用 B3 清理任务驱动。
- **涉及文件**：`app/services/data_cache_service.py`。
- **风险等级**：低
- **验证**：`/health/cache` 显示 materialized 域状态；清理任务覆盖该域。

### B9. GEE 凭据 SQLite 无清理
- **根因**：GEE 凭据表无清理任务，过期凭据累积。
- **严重度**：低
- **解决方案**：新增 Beat 任务清理过期凭据（高风险区：GEE 凭据加解密依赖 `BACKEND_GEE_CREDENTIALS_ENCRYPTION_KEY`，清理仅删过期项，不动加密密钥）。
- **涉及文件**：`app/services/gee_credentials_repository.py`、`app/tasks/cleanup_tasks.py`。
- **风险等级**：中（涉及高风险区凭据，须确保只删 expired 状态且不破坏加解密链路）
- **验证**：`pytest tests/test_gee_bridge_service.py -q`；验证未过期凭据不受影响。

### B10. 测试污染目录（artifacts_validation1-5、workflow_state_validation1-5 等）
- **根因**：测试用真实 `.data/` 子目录且未隔离/未清理。
- **严重度**：低
- **解决方案**：测试统一使用 `tmp_path` fixture 或 `ENVIRONMENT=test` 专属目录（如 `.data/test/`），CI 每次运行后清理；`conftest.py` 加 autouse fixture 测试结束清理生成目录。
- **涉及文件**：`app/tests/conftest.py`。
- **风险等级**：低
- **验证**：本地跑全量 pytest 后 `.data/` 不残留 `*_validation*` 目录。

## 4. 后端目录结构与代码依赖

### C1. services/ 50 个扁平文件，分组不彻底
- **根因**：`workflow/` 子包已有 9 文件，但另有 6 个 `workflow_*` 顶层文件同域未纳入；`weather_*/gee_*/download_*/config_*/tile_*/provider_*` 系列散落顶层。
- **严重度**：中
- **解决方案**（FastAPI 分层 + 按域子包组织）：
  - 按领域重组为子包：`services/workflow/`（吸收 6 个 `workflow_*`）、`services/weather/`、`services/gee/`、`services/download/`、`services/config/`、`services/tile/`、`services/provider/`。
  - 每个子包内遵循 `service.py`（业务逻辑）/ `repository.py`（数据访问）分离。
  - 用 `__init__.py` 显式导出公共 API，控制对外可见面。
- **涉及文件**：`app/services/` 全部 + 各 import 处。
- **风险等级**：中（大规模 import 路径迁移，需配合 ruff/mypy 全量校验，建议分域渐进迁移，配合 re-export 垫片保持兼容）
- **验证**：`pre-commit run --all-files`；`pytest tests/test_workflow_routes.py tests/test_business_regression.py -q`。

### C2. submission_service → tasks 反向依赖
- **根因**：service 层直接 import task 层，形成 service→task→service 循环依赖隐患，破坏分层方向（依赖应向内/向下）。
- **严重度**：高
- **解决方案**（依赖倒置 + 任务薄编排）：
  - 依赖倒置：service 不直接 import task，通过 `celery_app.send_task("task.name", args=...)` 字符串名派发，或定义 `TaskDispatcher` 接口由 service 依赖、task 层实现注入。
  - 更优解：将"提交任务"动作上移到 router/application 层（router 调 service 业务校验 → router 调 task 派发），service 保持纯业务逻辑。
  - task 层应薄编排：只做"读入参→调 service→写结果→发事件"，业务逻辑全在 service。
- **涉及文件**：`app/services/workflow/submission_service.py`、`app/tasks/workflow_tasks.py`、`app/services/workflow/lifecycle_service.py`。
- **风险等级**：中（依赖倒置需重构调用链，但消除循环依赖是结构性收益）
- **验证**：ruff 自定义规则禁止 `app/services/**` import `app/tasks/**`；`pytest tests/test_workflow_routes.py -q`。

### C3. 路由分裂三处 + 命名不统一 + docstring 失真

- **涉及文件**：`app/api/routers/__init__.py`、`app/api/config_routes.py`、`app/api/gee_config_routes.py`、`app/api/weather_tile_routes.py`、`app/main.py`。

- **涉及文件**：`app/services/python_provider_bridge_service.py`、`Code/algorithms/providers/Python/pyproject.toml`、`start_fastapi.py`、`conftest.py`。
- **风险等级**：中（动态 import 改注册表需改动算法接入流程；正式打包需协调 algorithms 包结构）

## 8. 假设与决策

1. **本报告为只读分析产物**，不修改任何文件；所有方案供逐项决策执行。
2. **风险等级标注**遵循"先分析后定夺"偏好：低=可安全直接执行；中=需配套测试与渐进迁移；高=需充分评审与测试环境验证后再上主链。
3. **B4 spec_version 嵌入 key** 是天气缓存"复活"治本方案，但属高风险且影响天气热路径，建议先在测试环境充分验证。
4. **B1 统一 CacheManager** 是缓存域治理基座，B3/B5/B6/B7/B8 均依赖其注册表与失效入口，应优先于其他缓存项推进。
5. **C2 依赖倒置** 是后端分层正确性前提，C1 重组应在 C2 模式确立后进行，避免重组时固化错误依赖方向。
6. **D5 移除 cesium** 须与团队确认 3D 地球功能是否仍为路线图项（AGENTS.md 注明"Cesium 依赖已引入但非默认主链"）；若未来需启用，应改为按需懒加载而非默认重依赖。
7. **B9 GEE 凭据清理** 与 **B7 Redis 分库** 涉及 AGENTS.md 标注的高风险区（GEE 凭据加密、Redis 运行态），执行前须确认鉴权与加密约束。
8. 前端 D1/D2 拆分属高风险，建议配合 re-export 垫片向后兼容，分批迁移消费端，每批配套组件测试。
